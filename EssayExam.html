Week 9 · ACD Module 7

AWS Lambda

อ่านบทเต็ม Week 9 ข้อสอบปรนัยของบทนี้ สรุปหน้าเดียว
โจทย์

บริษัทหนึ่งต้องการระบบที่ เมื่อผู้ใช้อัปโหลดรูปลง S3 bucket (S3-source) แล้ว ระบบจะแปลงรูปเป็น .PNG และเก็บลงอีก bucket (S3-dest) อัตโนมัติ โดยใช้ AWS Lambda

  • ก. AWS Lambda คืออะไร และต่างจากการรันโค้ดบน EC2 อย่างไรในแง่การดูแลระบบและการจ่ายเงิน
  • ข. ในระบบนี้ S3 เรียก Lambda แบบ synchronous หรือ asynchronous จงอธิบายความต่างของสองแบบนี้
  • ค. ต้องตั้งสิทธิ์ (permission) อะไรบ้างระบบนี้จึงจะทำงานได้
  • ง. ถ้าผู้ใช้บ่นว่า "ครั้งแรกที่ใช้งานช้ากว่าปกติ" สาเหตุคืออะไร และแก้อย่างไร
แนวคำตอบ

ก. Lambda คือบริการ serverless compute ที่รันโค้ดเมื่อมี event มากระตุ้น โดยเราไม่ต้องสร้างหรือดูแลเซิร์ฟเวอร์

  • การดูแล: เราดูแลแค่ โค้ด ส่วน AWS ดูแลเครื่อง OS การ patch และการ scale ให้ ต่างจาก EC2 ที่เราต้องดูแล OS เอง
  • การจ่ายเงิน: จ่ายเฉพาะตอนโค้ดรัน (scale to zero ตอนว่างไม่เสียเงิน) ต่างจาก EC2 ที่เปิดเครื่องไว้ก็เสียเงิน

ข. S3 เรียก Lambda แบบ asynchronous

SynchronousAsynchronous
ตัวอย่างAPI GatewayS3

ถ้า errorส่ง error กลับให้ผู้เรียก Lambda ไม่ retry ให้Lambda retry ให้ได้ 2 ครั้ง (รวมลองสูงสุด 3 ครั้ง)

ค. สิทธิ์มี 2 ฝั่ง

  1. ขาเข้า — S3 ต้องมีสิทธิ์เรียก Lambda: ตั้งที่ resource-based policy ของ function (อนุญาต lambda:InvokeFunction)
  2. ขาออก — Lambda ต้องมีสิทธิ์ใช้ S3: ตั้งที่ IAM execution role ให้ อ่าน S3-source (s3:GetObject) และ เขียน S3-dest (s3:PutObject)

ง. สาเหตุคือ cold start — ครั้งแรก (หรือหลังว่างนาน) AWS ต้องเตรียม environment ใหม่ก่อนรันโค้ด จึงช้า (ดูได้จาก Init Duration ใน CloudWatch Logs)

  • แก้ด้วย Provisioned concurrency ซึ่งเตรียม environment ไว้ให้อุ่นตลอด (มีค่าใช้จ่ายเพิ่ม)
  • (ต่างจาก Reserved concurrency ที่ใช้กันโควตาและเป็นเพดาน ไม่ได้ช่วยเรื่อง cold start)

Week 10 · ACD Module 8 + 9

Containers บน AWS และ Caching

อ่านบทเต็ม Week 10 ข้อสอบปรนัยของบทนี้ สรุปหน้าเดียว
โจทย์

ส่วนที่ 1 (Container)

  • ก. Container ต่างจาก Virtual Machine อย่างไร และทำไม container จึงช่วยแก้ปัญหา "works on my machine"
  • ข. บริษัทจุดชาร์จรถ EV มี container ไม่ถึง 20 ตัว ช่วงวันหยุดยาว traffic เพิ่ม 3–4 เท่า ควรใช้ ECS หรือ EKS และควรเลือก launch type แบบ EC2 หรือ Fargate เพราะอะไร
  • ค. ถ้าต้องการอัปเดตแอปบน Elastic Beanstalk โดยไม่มี downtime และ rollback ง่าย ควรเลือก deployment policy แบบใด อธิบายเทียบกับแบบ All at once

ส่วนที่ 2 (Caching)

  • ง. ทำไมต้องทำ caching และข้อมูลแบบไหนเหมาะกับการ cache
  • จ. อธิบายความต่างของ Lazy Loading กับ Write-Through ใน ElastiCache
  • ฉ. จะเพิ่ม cache hit ratio ของ CloudFront ได้อย่างไร
แนวคำตอบ

ก.

Virtual MachineContainer
OSทุก VM มี OS ของตัวเองใช้ kernel ของ host ร่วมกัน
ผลหนัก เปลืองทรัพยากรเบา เริ่มเร็ว ใช้ทรัพยากรคุ้ม

Container รวม code, runtime, system tools และ library ไว้เป็นหน่วยมาตรฐานเดียว (เหมือนตู้คอนเทนเนอร์ขนส่ง) จะไปรันบน host ไหนก็ได้ผลเหมือนเดิม (consistency) จึงแก้ปัญหา works on my machine

ข. ควรใช้ ECS เพราะ container ไม่มาก แต่ต้องการ HA และ scaling — ECS ทำได้ ถูกกว่าและง่ายกว่า (EKS เหมาะกับ container จำนวนมาก หรือมี Kubernetes อยู่แล้ว และแพงกว่า)

  • Launch type: traffic ขึ้นลงไม่แน่นอน (วันหยุดพุ่ง 3–4 เท่า) และทีมไม่อยากเฝ้าระบบ → Fargate เพราะ scale ตาม demand และไม่ต้องดูแล infra (แลกกับค่าใช้จ่ายที่คาดเดายาก)
  • ถ้า demand คงที่และต้องคุมงบ จะเลือก EC2 launch type (จ่ายตามเครื่องที่ provision, ใช้ Reserved Instance ลดราคาได้)

ค. เลือก Immutable — สร้าง Auto Scaling Group ชุดใหม่ด้วยเวอร์ชันใหม่ ผ่าน health check แล้วจึงย้าย traffic ไป ของเดิมยังอยู่จึง rollback ง่ายและไม่มี downtime (ข้อแลก: ช่วงหนึ่งมี 2 ASG ค่าใช้จ่ายสูงขึ้น)

  • เทียบกับ All at once: อัปเดตทุกเครื่องพร้อมกัน เร็วที่สุดแต่มี downtime

ง. caching ช่วย ลด latency / response time และ ลดภาระของ origin หรือ database โดยเก็บข้อมูลไว้ใกล้ผู้ใช้ในหน่วยความจำความเร็วสูง (มี TTL)

  • เหมาะกับข้อมูลที่ อ่านบ่อยแต่เปลี่ยนไม่บ่อย เช่น feed ของ social network, ผลคำนวณที่ใช้ compute หนัก
  • ไม่เหมาะกับข้อมูลที่เปลี่ยนบ่อยมาก

จ.

  • Lazy Loading: เขียนลง cache ตอนเกิด cache miss (app อ่านจาก database แล้วค่อยเก็บลง cache) → เก็บเฉพาะข้อมูลที่มีคนขอ แต่ข้อมูลอาจเก่าได้
  • Write-Through: ทุกครั้งที่อัปเดต database ก็เขียนลง cache พร้อมกัน → ข้อมูลใน cache เป็นปัจจุบันเสมอ

ฉ.

  1. อย่าให้ cache key ละเอียดเกินไป — ไม่ใส่ query string, header หรือ cookie ที่ไม่จำเป็นลงใน key (default key = domain + URL path)
  2. ตั้ง TTL ให้เหมาะสม (minimum, maximum, default)

Week 11 · ACD Module 10

Messaging Services (SQS, SNS, Kinesis)

อ่านบทเต็ม Week 11 ข้อสอบปรนัยของบทนี้ สรุปหน้าเดียว
โจทย์

ร้านกาแฟออนไลน์ต้องการระบบรับออร์เดอร์ที่รองรับลูกค้าจำนวนมาก

  • ก. การประมวลผลแบบ synchronous กับ asynchronous ต่างกันอย่างไร และทำไม messaging service จึงช่วยให้ระบบ scale ได้ดี
  • ข. อธิบายความต่างของ Amazon SQS, Amazon SNS และ Amazon Kinesis
  • ค. อธิบายการทำงานของ visibility timeout และ Dead-Letter Queue (DLQ) ใน SQS
  • ง. ออร์เดอร์ใหม่หนึ่งรายการต้องส่งไปทั้ง ระบบจัดส่ง ระบบตัดสต็อก และระบบส่งอีเมล และทุกงานต้อง ถูกประมวลผลแน่นอน ควรออกแบบอย่างไร
แนวคำตอบ

ก.

  • Synchronous: client ส่ง request แล้วต้อง รอ จนงานเสร็จ ระหว่างนั้นต้องถือ connection ไว้ → ตอบเร็ว แต่กิน resource มาก client เยอะแล้ว scale ไม่ดี
  • Asynchronous: ระบบตอบแค่ "ได้รับแล้ว" (acknowledge) แล้วค่อยประมวลผลทีหลัง → รับ client ได้มาก scale ดี แต่ไม่รู้ว่าจะเสร็จเมื่อไร (เหมือนโรงพยาบาลรัฐ: วางบัตรแล้วรอเรียกคิว)
  • Messaging service เป็น ตัวกลาง: ผู้ส่งวางข้อมูลไว้แล้วไปทำงานต่อได้เลย ผู้รับมารับไปเองเมื่อพร้อม service จึง ไม่ต้องคุยกันตรง ๆ (loosely coupled) ถ้าฝั่งรับช้าหรือล่ม งานก็รออยู่ไม่หาย

ข.

ค.

  • Visibility timeout (default 30 วินาที): เมื่อ consumer ดึง message ไป message ยังไม่ถูกลบ แต่ถูกซ่อนจาก consumer อื่น ถ้าประมวลผลสำเร็จ consumer จะลบ message ถ้าหมดเวลาแล้วยังไม่สำเร็จ (เช่น consumer crash) message จะ กลับมาให้ consumer อื่นทำแทน → ไม่มีงานหาย
  • DLQ: message ที่ประมวลผลไม่สำเร็จซ้ำ ๆ จนครบ maxReceiveCount จะถูกย้ายไปอีก queue หนึ่ง เพื่อ ไม่ให้ค้างในคิวหลัก และ แยกออกมาหาสาเหตุ ได้ง่าย

ง. ใช้ SNS fan-out ร่วมกับ SQS

ออร์เดอร์ใหม่ ─► SNS Topic ─┬─► SQS: จัดส่ง  ─► ระบบจัดส่ง
                           ├─► SQS: สต็อก   ─► ระบบตัดสต็อก

  • SNS ส่งออร์เดอร์เดียวไปหลายปลายทางพร้อมกัน (one-to-many)
  • SQS คั่นหน้าแต่ละระบบ เพราะ SQS reliable — ถ้าระบบปลายทางล่มชั่วคราว ออร์เดอร์ยังรออยู่ในคิว ไม่หาย (SNS อย่างเดียวไม่ได้ reliable โดย default)

Week 12 · ACD Module 11 + 12

Step Functions และ Developing Secure Applications

อ่านบทเต็ม Week 12 ข้อสอบปรนัยของบทนี้ สรุปหน้าเดียว
โจทย์

ส่วนที่ 1 (Step Functions)

  • ก. AWS Step Functions แก้ปัญหาอะไรของระบบ microservices และมีข้อดี / ข้อแลกเปลี่ยนอะไร
  • ข. จาก demo Stock Trading (ดึงราคาหุ้น → เทียบกับ 50 → ซื้อหรือขาย → ส่ง SNS) จงบอกว่าแต่ละขั้นใช้ state type อะไร และถ้าได้ราคา 70 ผลจะเป็นอย่างไร
  • ค. Standard Workflow กับ Express Workflow ต่างกันอย่างไร

ส่วนที่ 2 (Security)

  • ง. การทำ TLS termination ที่ ALB ต่างจากการเข้ารหัสแบบ end-to-end ด้วย NLB อย่างไร
  • จ. ทำไมจึงควรใช้ temporary credential จาก STS แทน long-term credential
  • ฉ. Cognito User Pool กับ Identity Pool ต่างกันอย่างไร
แนวคำตอบ

ก. ในระบบ microservices ที่มีหลาย service ต่อกัน เวลามีปัญหาต้อง เปิดดูทีละ service ระบบใหญ่จะไล่หาปัญหายาก Step Functions เป็น service orchestration ที่ทำให้ เห็น workflow ทั้งหมดในที่เดียว เจาะดูได้ว่า error เกิดที่ขั้นไหน

  • ข้อดี: ทำงานอัตโนมัติตามลำดับและเงื่อนไข, retry อัตโนมัติ, เก็บ log ทุกขั้น, แก้ปัญหาได้เร็ว downtime น้อยลง, maintain ง่าย
  • ข้อแลก: ค่าใช้จ่ายเพิ่มขึ้น (เคส Prime Video ย้ายออกไปเป็น monolith บน EC2 แล้วลด cost ได้ราว 90% เพราะ volume สูงมาก)
  • resilience จะได้จริงหรือไม่ ขึ้นกับการ config ของเรา เช่นตั้ง retry กี่ครั้ง

Week 13 · ACD Module 13

DevOps และ CI/CD บน AWS

อ่านบทเต็ม Week 13 ข้อสอบปรนัยของบทนี้ สรุปหน้าเดียว
โจทย์
  • ก. DevOps คืออะไร และช่วยแก้ปัญหาของการแยกทีม Dev กับ Ops แบบเดิมอย่างไร
  • ข. อธิบายขั้นตอนของ CI/CD pipeline พร้อมบอกบริการ AWS ที่ใช้ในแต่ละขั้น
  • ค. Continuous Delivery กับ Continuous Deployment ต่างกันอย่างไร
  • ง. CloudFormation และ AWS SAM ช่วยงาน DevOps อย่างไร
แนวคำตอบ

ก. DevOps ไม่ใช่เครื่องมือ แต่เป็น วัฒนธรรมการทำงานและกระบวนการ ที่ให้ Dev กับ Ops ทำงานร่วมกันในลูปเดียว และรับผิดชอบร่วมกัน

  • ปัญหาแบบเดิม: Dev ดูแลแอป Ops ดูแล infra แยกกัน แอปที่รันบนเครื่อง Dev ได้กลับพังบน infra ของ Ops เพราะ environment ต่างกัน ("works on my machine") deploy ช้าและโทษกันไปมา
  • DevOps แก้โดย: ทำ environment ทุกระดับ (Dev/Test/Prod) ให้เหมือนกัน, ใช้ automation ทุกขั้น และ Infrastructure as Code ให้ deploy ซ้ำได้ผลเหมือนเดิม → ส่งมอบได้ เร็ว เชื่อถือได้ ขยายได้ และปลอดภัย
  • ความสำเร็จขึ้นกับ คนและความเข้าใจ มากกว่าเครื่องมือ

ข.

ค.

  • Continuous Delivery: ก่อนขึ้น production ต้องมีคน review และกด manual approval
  • Continuous Deployment: อัตโนมัติทั้งหมด ผ่าน test แล้วขึ้น production ทันที ไม่ต้องมีคนอนุมัติ

ง.

  • CloudFormation (Infrastructure as Code): เขียน template (JSON/YAML) ที่ต้องมีส่วน Resources แล้วได้ Stack ใน region นั้น → สร้าง infra ซ้ำได้เหมือนเดิมทุกครั้ง ถ้าต้อง deploy หลาย account / หลาย region ใช้ StackSets
  • AWS SAM: framework สำหรับ serverless ที่ ต่อยอดจาก CloudFormation เขียน Lambda + IAM + API Gateway + DynamoDB ใน template สั้น ๆ และใช้ SAM CLI ทดสอบบนเครื่อง local ก่อน deploy จึงไม่เสียค่าใช้จ่ายโดยไม่จำเป็น และใช้ร่วมกับ CodePipeline ได้
