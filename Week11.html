01

ภาพรวมของ Messaging

สรุปใน 1 ประโยค

Messaging service คือตัวกลางที่ให้ผู้ส่งวางข้อมูลไว้แล้วไปทำงานต่อ ส่วนผู้รับมารับไปเองเมื่อพร้อม service จึงไม่ต้องคุยกันตรง ๆ

  • โมดูลก่อนหน้าเรียน Caching, Container และ Serverless ไปแล้ว โมดูลนี้เรียน Messaging Service ซึ่งเป็น "ตัวกลาง" เชื่อม service ต่าง ๆ เข้าด้วยกัน
  • มีประโยชน์มากกับระบบแบบ Microservice หรือ Serverless
  • แนวคิด: service ที่ส่ง ไม่ต้องคุยกับ service ที่รับโดยตรง แค่เอาข้อมูลไปวางไว้ที่ messaging service แล้วอีกฝั่งจะมารับไปเอง (ผูกกันหลวม ๆ — loosely coupled)

เปรียบเทียบให้เห็นภาพ: แทนที่จะโทรหาเพื่อนแล้วต้องรอเพื่อนรับสาย (เรียกตรง) เราฝากของไว้ที่ล็อกเกอร์ แล้วเพื่อนมาเปิดเอาไปเมื่อพร้อม ถ้าเพื่อนยังไม่ว่าง ของก็ยังอยู่ในล็อกเกอร์

ลองเล่น

เรียกตรง vs ผ่าน messaging — ถ้าผู้รับล่มจะเกิดอะไร

    Managed service ของ AWS ที่เรียนมี 3 ตัว

    Serviceชื่อเต็มใช้กับงานแบบ
    Amazon SQSSimple Queue Serviceส่งเป็นชุดหรือทีละ message (batch processing)
    Amazon SNSSimple Notification Serviceส่งเป็นชุดหรือทีละ message (batch processing)
    Amazon KinesisKinesis Data Streamsข้อมูลไหลเข้ามาต่อเนื่องแบบ real-time (stream processing)
    จุดหลอกในข้อสอบ
    • SQS และ SNS = งานแบบ message / batch ส่วน Kinesis = stream real-time (ช้อยหลอกมักสลับกัน)
    • ผ่านตัวกลางแล้วไม่ได้แปลว่า "ได้ผลทันที" — การส่งผ่านตัวกลางเป็นแบบ async
    02

    Synchronous กับ Asynchronous Processing

    สรุปใน 1 ประโยค

    Sync ตอบเร็วแต่ต้องถือ connection ไว้จน resource หมด scale ไม่ดี ส่วน async ตอบแค่ "รับแล้ว" จึงรับ client ได้มากและ scale ดี แต่ไม่รู้ว่างานจะเสร็จเมื่อไร

    Synchronous

    • Client ส่ง request ไปที่ Service A → A ต้องสั่งให้ B ทำงาน และ รอ B ตอบกลับ ก่อน A ถึงจะตอบ client ได้
    • ระหว่างนั้นทุกฝ่ายต้อง คงการเชื่อมต่อ (maintain connection/state) ไว้ตลอด
    • A ทำงานหนักที่สุด เพราะต้องถือ connection ทั้งกับ client และ B
    • ข้อดี: ตอบสนองเร็ว เหมาะกับงานที่ต้องได้ผลทันทีหรือ real-time
    • ข้อเสีย: กิน resource มาก ยิ่งมี client มาก resource ของ A ยิ่งลดลงจนอาจให้บริการไม่ได้ → scale ได้ไม่ดี

    Asynchronous

    • A แค่ตอบ client ว่า ได้รับ request แล้ว (acknowledge) client ก็ถือว่าจบงานของตัวเอง แล้ว A ค่อยส่งงานต่อให้ B ประมวลผลทีหลัง
    • SQS และ SNS ทำงานแบบนี้
    • ข้อดี: รองรับ client จำนวนมากได้ และ scale ได้ดี
    • ข้อเสีย: การันตีไม่ได้ว่างานจะเสร็จเมื่อไร

    ตัวอย่างโรงพยาบาลของผู้สอน

    โรงพยาบาลรัฐ = Asyncโรงพยาบาลเอกชน = Sync
    จำนวนคนไข้เป็นร้อยคนน้อย
    ขั้นตอนวางบัตรนัดในตะกร้า → วัดความดัน (ได้ acknowledge) → นั่งรอเรียกคิวเจ้าหน้าที่มาถามว่ารอนานหรือยัง แล้วช่วยเร่งให้
    ผลได้ตรวจแน่นอน แต่ไม่รู้ว่าเมื่อไรสะดวกและเร็ว แต่ค่าใช้จ่ายสูง (เหมือน sync ที่กิน resource มาก)
    แบบจำลอง

    Service A รับ client ได้แค่ไหน

    สมมติ Service A ถือ connection ค้างไว้ได้สูงสุด 100 ตัว และ B ประมวลผลได้ 20 งานต่อนาที

      จุดหลอกในข้อสอบ
      • ฝั่งที่ทำงานหนักที่สุดใน sync คือ A (ตัวกลางที่ถือ connection สองฝั่ง) ไม่ใช่ B
      • "ได้รับ acknowledge" ≠ "งานเสร็จแล้ว" — async ได้แค่รู้ว่าระบบรับเรื่อง
      • งานที่ผู้ใช้ต้องเห็นผลทันทีบนหน้าจอ → sync แม้ SQS จะ reliable ก็ตาม

      รูปแบบของ Messaging 3 แบบ

      สรุปใน 1 ประโยค

      SQS = queue แบบ one-to-one ที่ consumer มาดึง, SNS = pub/sub แบบ one-to-many ที่ push ไปทุก subscriber, Kinesis = stream ข้อมูลไหลต่อเนื่อง

      รูปแบบServiceลักษณะ
      Message QueueSQSOne-to-one: Producer ส่ง message เข้า Queue แล้ว Consumer มา ดึง (poll) ไปประมวลผล
      Publish/SubscribeSNSOne-to-many: Publisher ส่ง message ไปที่ Topic แล้ว SNS ส่งต่อ (push) ไปให้ Subscriber ทุกตัว
      Data StreamKinesisข้อมูลไหลเข้ามาต่อเนื่อง แล้ว Consumer ดึงไปประมวลผล
      ดูการทำงาน

      Queue vs Pub/Sub vs Stream

      ความต่างที่ต้องจำ (ตามที่ผู้สอนเน้น)

      • SQS การันตีว่าส่งถึงจริง (reliable) เพราะเก็บ message ไว้จนกว่า consumer จะประมวลผลสำเร็จ
      • SNS ส่ง (push) ไปให้ subscriber แล้วลบ message ทิ้งได้เลย ไม่ได้การันตีแบบ SQS
      เสริม

      SNS ไม่ได้เก็บ message ไว้ให้ใครมาดึงทีหลังแบบ SQS แต่มี delivery retry policy ในตัวสำหรับการส่งไปยัง endpoint (ปรับแต่งได้สำหรับ HTTP/S) ส่วน DLQ ต้องตั้งเองต่อ subscription — ในข้อสอบให้ยึดหลักของผู้สอน: SQS reliable โดย default, SNS ต้องตั้งค่าเพิ่ม

      จุดหลอกในข้อสอบ
      • ต้องการให้ "หลายระบบ" ได้ message เดียวกัน → SNS (fan-out) ไม่ใช่ SQS queue เดียวที่มีหลาย consumer
      • SQS = consumer poll / SNS = push (ช้อยหลอกมักสลับ)
      • "shard" เป็นคำของ Kinesis, "topic" ของ SNS, "queue" ของ SQS
      04 · สอนละเอียดที่สุด

      Amazon SQS

      สรุปใน 1 ประโยค

      SQS reliable เพราะ message ไม่ถูกลบจนกว่าจะประมวลผลสำเร็จ ระหว่างประมวลผลถูกซ่อนด้วย visibility timeout (default 30 วินาที) และถ้าล้มเหลวซ้ำจนครบ maxReceiveCount จะถูกย้ายไป DLQ

      แนวคิดหลัก

      • Fully managed: แค่ตั้งชื่อ queue แล้วใช้ค่า default ก็ใช้งานได้ (คล้าย DynamoDB) AWS ดูแลเรื่อง High Availability, Scaling และ Resilience ให้
      • เก็บหลายสำเนา: เบื้องหลังเก็บ message ไว้หลายชุดบนหลาย SQS server ถ้า disk ตัวหนึ่งเสีย ข้อมูลก็ไม่หาย
      • Keyword ของ SQS คือ "Reliable": ส่ง message ได้แน่นอน แม้ข้อมูลปริมาณมากและ throughput สูง
      • Pay-as-you-go: ใช้มากจ่ายมาก ใช้น้อยจ่ายน้อย

      ขั้นตอนการทำงาน

      1. Producer ส่ง message เข้า queue (SendMessage) แล้วไปทำงานอื่นต่อได้ทันที
      2. Consumer ดึง message ไปประมวลผล (ReceiveMessage)
      3. ถ้าประมวลผล สำเร็จ consumer แจ้งกลับมา แล้ว message ถูกลบออกจาก queue
      4. ถ้า ไม่สำเร็จ message ยังคงอยู่ใน queue

      เสริม "แจ้งกลับมา" คือ consumer เรียก DeleteMessage เอง ถ้าใช้ Lambda ผ่าน event source mapping (Week 9) Lambda จะลบให้อัตโนมัติเมื่อ function สำเร็จ

      Visibility Timeout (ค่า default 30 วินาที)

      • เมื่อ Consumer 1 ดึง message A ไป message A ยังไม่ถูกลบ แต่ consumer อื่นจะ "มองไม่เห็น" ชั่วคราว
      • ถ้าหมดเวลาแล้ว Consumer 1 ยังไม่แจ้งว่าสำเร็จ message A จะ กลับมาให้เห็นใน queue และ consumer ตัวอื่นดึงไปทำแทนได้
      • นี่คือกลไกที่ทำให้ SQS เชื่อถือได้
      • เสริม ตั้งได้ 0 วินาที – 12 ชั่วโมง ควรตั้งให้ นานกว่าเวลาที่ใช้ประมวลผล message หนึ่งตัว ไม่อย่างนั้น message จะโผล่กลับมาก่อนประมวลผลเสร็จแล้วถูกประมวลผลซ้ำ

      Dead-Letter Queue (DLQ)

      • message ที่ประมวลผลไม่สำเร็จซ้ำ ๆ จนครบจำนวนครั้งที่ตั้งไว้ (maxReceiveCount เช่น 2 ครั้ง) จะถูกย้ายไปไว้อีก queue หนึ่ง
      • ประโยชน์: (1) เคลียร์พื้นที่ของ queue หลัก ไว้ให้ message ที่ประมวลผลได้จริง (2) แยก message ที่มีปัญหาออกมา ให้หาสาเหตุ (troubleshoot) ได้ง่าย
      • เสริม DLQ ของ FIFO queue ต้องเป็น FIFO, DLQ ของ standard queue ต้องเป็น standard

        ประเภทของ Queue: Standard vs FIFO

        สรุปใน 1 ประโยค

        Standard (default) throughput สูงแต่ลำดับไม่แน่นอน ส่วน FIFO ได้ลำดับแน่นอนแต่ throughput จำกัดและตัวช้าข้างหน้าทำให้ตัวหลังต้องรอ

        Standard (ค่า default)FIFO (First-In-First-Out)
        ลำดับbest-effort ordering message ที่มาทีหลังอาจถูกประมวลผลก่อนได้message ที่มาก่อนต้องประมวลผลเสร็จก่อน ตัวถัดไปถึงจะเริ่มได้
        Throughputสูงแทบไม่จำกัดจำกัดกว่า และมีโอกาสเกิด delay มากกว่า
        ใช้เมื่อลำดับไม่สำคัญ ต้องการรับโหลดมากลำดับสำคัญ
        การส่ง เสริมat-least-once (อาจได้ message ซ้ำ)exactly-once processing (ไม่ซ้ำ)

        ผู้สอนยกตัวอย่าง FIFO ว่าเหมือน ต่อคิวซื้อกองทุนลดหย่อนภาษีตอนปลายปี ถ้าคนข้างหน้าใช้เวลาเป็นชั่วโมง คนข้างหลังก็ต้องรอ

        Polling, Retention และคำสั่ง CLI

        สรุปใน 1 ประโยค

        Short polling ถามบ่อยจึงเร็วแต่แพง long polling ถามน้อยครั้งจึงถูกกว่า (trade-off ระหว่าง cost กับ response time) และ message ที่ค้างเกิน retention period จะถูกลบทิ้ง

        Short Polling กับ Long Polling

        Short pollingLong polling
        วิธีถามถามบ่อย ๆรอนานขึ้นก่อนตอบ ถามน้อยครั้งลง
        ความเร็วตอบกลับได้ response เร็วต้องยอมรับ delay ได้ (ตามที่ผู้สอนสรุป)
        ค่าใช้จ่ายจำนวนครั้งที่ถามมากขึ้น → แพงกว่าถูกกว่า

        เป็นการแลกกัน (trade-off) ระหว่าง cost กับ response time AWS จึงให้ผู้ใช้ตั้งค่าเลือกเอง

        เสริม

        ในทางเทคนิค short polling ตอบกลับทันทีแม้ queue ว่าง (ได้ empty response บ่อย) ส่วน long polling ให้ ReceiveMessage รอได้สูงสุด 20 วินาที (WaitTimeSeconds) และ ตอบกลับทันทีที่มี message เข้ามา จึงลด empty response และค่าใช้จ่าย AWS แนะนำให้ใช้ long polling ในกรณีส่วนใหญ่

        การลบ message และ Retention Period

        • สั่งลบ message เองได้ แต่โดยปกติ message จะถูกลบเมื่อประมวลผลสำเร็จ

        • เสริม retention ค่า default 4 วัน ตั้งได้ 1 นาที – 14 วัน

        Security ของ SQS และ SNS

        สรุปใน 1 ประโยค

        ควบคุมสิทธิ์ด้วย IAM + resource-based policy, เข้ารหัสด้วย SSE ผ่าน KMS และเชื่อมจาก VPC แบบ private ผ่าน Interface Endpoint (มีค่าใช้จ่าย)

        • ควบคุมการเข้าถึงด้วย IAM และ Resource-based policy (SQS policy)
        • เข้ารหัสข้อมูลด้วย Server-side encryption (SSE) ผ่าน AWS KMS
        • SQS อยู่นอก VPC จึงต้องเชื่อมผ่าน VPC Endpoint — ผู้สอนตรวจเอกสารหลังพักแล้วสรุปว่า SQS ใช้ Interface Endpoint ซึ่งเป็น private connection และ มีค่าใช้จ่าย
        • เสริม Gateway Endpoint (ไม่มีค่าใช้จ่าย) รองรับแค่ S3 กับ DynamoDB
        • SNS: เหมือน SQS คือใช้ IAM, SSE ผ่าน KMS และ VPC Interface Endpoint (ผู้สอนบอกว่าจะไปตรวจยืนยันอีกที)
        ลองเลือก

        EC2 ใน private subnet ต้องเชื่อม service ไหนด้วย endpoint แบบไหน

        เลือก endpoint ที่ใช้ได้และประหยัดที่สุดสำหรับแต่ละ service

          Architecture ตัวอย่าง: Event-driven

          สรุปใน 1 ประโยค

          อัปโหลดรูป → S3 trigger Lambda → Lambda ส่ง URI เข้า SQS → EC2 ใน Auto Scaling Group ดึงไปแปลงรูป โดย scale EC2 ตามความยาวของ queue

          ผู้ใช้อัปโหลดรูป → S3 (create object event)
   → S3 Event Notification trigger Lambda
   → Lambda ส่ง URI ของรูปไปไว้ใน SQS
   → EC2 ใน Auto Scaling Group ดึง message ไปแปลงรูป → เขียนลง S3 อีก bucket
          • เรียกว่า event-driven เพราะระบบทำงานเฉพาะตอนเกิด event
          • Lambda กับ SQS คิดเงินเฉพาะตอนทำงาน ส่วน EC2 ต้องเปิดตลอด
          • ใช้ ความยาวของ queue เป็นตัวกำหนดการ scale ได้: queue สั้นใช้ EC2 ตัวเดียว queue ยาวถึงระดับที่ตั้งไว้ก็เพิ่มจำนวน EC2
          • เสริม metric ที่ใช้คือ ApproximateNumberOfMessagesVisible ใน CloudWatch
          แบบจำลอง

          Scale EC2 ตามความยาวของ queue (10 นาที)

          สมมติ EC2 1 ตัวแปลงรูปได้ 30 รูป/นาที, ASG มีขั้นต่ำ 1 ตัว สูงสุด 10 ตัว

            จุดหลอกในข้อสอบ
            • ผู้ trigger Lambda คือ S3 Event Notification ไม่ใช่ SQS / ผู้ส่ง URI เข้า SQS คือ Lambda ไม่ใช่ EC2
            • "ทุก component คิดเงินเฉพาะตอนทำงาน" ผิด — EC2 ต้องเปิดตลอด
            • metric ที่ใช้ scale คือ ความยาวของ queue ไม่ใช่ visibility timeout

            Amazon SNS

            สรุปใน 1 ประโยค

            SNS เป็น pub/sub ที่ push message เดียวไปหลายปลายทางพร้อมกัน (fan-out) กรอง message ได้ แต่ retry/DLQ ไม่ใช่ค่า default จึงไม่ reliable โดย default

            แนวคิดหลัก

            • เป็น Fully managed Pub/Sub คล้าย MQTT เลือกใช้เมื่อต้องการตั้งระบบได้เร็วและยืดหยุ่น แทนการติดตั้ง messaging service เอง
            • รองรับทั้ง one-to-many และ many-to-many
            • เลือกประเภท Topic ได้ทั้ง Standard และ FIFO
            • รองรับ Retry และ Dead-Letter Queue แต่ไม่ใช่ค่า default → SNS จึง ไม่ได้ reliable โดย default ต่างจาก SQS ที่ reliable โดย default
            • Subscriber / Endpoint ที่รองรับ: Lambda, SQS, Kinesis Data Firehose, HTTP/S, Email, SMS, Mobile Push Notification
            • มี Message Filtering สำหรับกรอง message ตามเงื่อนไขที่กำหนด (เสริม ตั้งเป็น filter policy ที่ subscription แต่ละตัว)

            Fan-out pattern

            message เดียวถูกส่งไป หลายปลายทางพร้อมกัน เช่น New Order Topic ส่งต่อไปที่ระบบ Fulfillment (ติดตามและจัดส่ง), Data Warehouse (ตัดสต็อก) และระบบอื่นอีกตัว

            แบบจำลอง

            SNS fan-out, filtering และ serverless image processing

            ประเภทออร์เดอร์

            กด Publish เพื่อดูว่า subscriber แต่ละตัวได้อะไร

            S3 → SNS Topic → fan out ไป SQS 3 queue → แต่ละ queue trigger Lambda ของตัวเอง → เขียนลง S3 ปลายทาง จ่ายเฉพาะตอนที่ระบบทำงาน

            ตัวอย่าง Image processing แบบ Serverless 100%

            อัปโหลดรูป → S3 (create object event ส่ง URI) → SNS Topic
   ├─► SQS: thumbnail → Lambda → S3 ปลายทาง
   ├─► SQS: mobile    → Lambda → S3 ปลายทาง
   └─► SQS: web       → Lambda → S3 ปลายทาง
            • SNS fan out ไปยัง SQS 3 queue แต่ละ queue trigger Lambda ของตัวเอง Lambda ดึงรูปต้นฉบับมาแปลง แล้วเขียนลง S3 ปลายทาง
            • จ่ายเฉพาะตอนที่ระบบทำงาน
            • ใส่ SQS คั่นเพื่อให้แต่ละงานได้ความ reliable ของ SQS (message รออยู่ในคิวจนประมวลผลสำเร็จ)

            Security

            เหมือน SQS คือใช้ IAM, SSE ผ่าน KMS และ VPC Interface Endpoint (ผู้สอนบอกว่าจะไปตรวจยืนยันอีกที)

            จุดหลอกในข้อสอบ
            • SNS ส่งหา Lambda ได้ — เหตุผลที่ใส่ SQS คั่นคือความ reliable ไม่ใช่ "SNS ส่ง Lambda ไม่ได้"
            • fan-out ทำโดย SNS ไม่ใช่ SQS
            • กรองให้ subscriber รับเฉพาะบาง message → message filtering (ไม่ใช่ FIFO / shard / visibility timeout)
            • RDS ไม่อยู่ในรายการ endpoint ของ SNS

            Amazon Kinesis Data Streams & Firehose

            สรุปใน 1 ประโยค

            Kinesis Data Streams รับข้อมูลไหลต่อเนื่องปริมาณมากโดยแบ่งเป็น shard และต้องตั้ง consumer เอง ส่วน Firehose แปลงข้อมูลในตัวโดยไม่ต้องมี compute แต่ส่งได้เฉพาะปลายทางที่รองรับ

            แนวคิดหลัก

            • Fully managed สำหรับ real-time data streaming ข้อมูลไหลเข้ามาต่อเนื่อง ปริมาณมาก ระดับ MB ต่อวินาที
            • Use case: financial transaction, social media feed, IT log, database event stream, real-time analytics, เกมออนไลน์
            • Producer มาจาก data source หลายแหล่ง ข้อมูลใน stream ถูกแบ่งเป็น Shard
            • ต้องตั้ง Consumer เอง เพื่อดึงข้อมูลไปประมวลผล เช่น EC2 (ควบคุมเองได้เต็มที่), Lambda (งานไม่ซับซ้อน) หรือ Kinesis Data Firehose
            • เสริม แต่ละ shard รับเขียนได้ราว 1 MB/s หรือ 1,000 records/s และอ่านได้ราว 2 MB/s ข้อมูลเก็บใน stream ค่า default 24 ชั่วโมง (ขยายได้ถึง 365 วัน) consumer หลายตัวอ่านข้อมูลชุดเดียวกันได้ ต่างจาก SQS ที่ message ถูกลบเมื่อประมวลผลแล้ว

            Data Streams กับ Data Firehose

            Data Streams + EC2/LambdaData Firehose
            Computeต้องสร้าง compute เองไม่ต้องสร้าง compute ประมวลผล/แปลงข้อมูล (transform) ในตัว
            ปลายทางเลือกที่เก็บผลลัพธ์ได้ หลากหลายกว่าส่งไปเก็บได้ เฉพาะ storage ที่ Firehose รองรับ เช่น S3

            เสริม ปลายทางของ Firehose เช่น S3, Redshift, OpenSearch, Splunk, HTTP endpoint การแปลงข้อมูลแบบกำหนดเองทำผ่าน Lambda ที่ Firehose เรียกให้

                ทบทวน

                สรุปหน้าเดียว — จุดที่น่าจะออกสอบ

                3 service

                • SQS = queue one-to-one (poll)
                • SNS = pub/sub one-to-many, fan-out (push)
                • Kinesis = streaming

                Sync vs Async

                • Sync เร็ว แต่กิน resource scale ไม่ดี
                • Async scale ดี แต่ไม่รู้ว่าเสร็จเมื่อไร

                Reliable

                • SQS reliable โดย default
                • SNS ไม่ใช่ — Retry และ DLQ ไม่ใช่ค่า default

                Visibility Timeout

                • default 30 วินาที
                • ซ่อน message ระหว่างประมวลผล หมดเวลาแล้วกลับมาให้ตัวอื่นทำ

                Dead-Letter Queue

                • แยก message ที่ล้มเหลวครบ maxReceiveCount
                • เคลียร์ queue หลัก + troubleshoot

                Standard vs FIFO

                • Standard (default) throughput สูง ลำดับไม่แน่นอน
                • FIFO ลำดับแน่นอน throughput จำกัด

                Polling

                • Short เร็วแต่แพง
                • Long ถูกแต่ช้ากว่า

                CLI

                • delete-message ≠ delete-queue
                • set-queue-attributes แก้ค่า

                Security

                • IAM + SQS policy, SSE-KMS
                • Interface Endpoint (มีค่าใช้จ่าย)
                • Gateway มีแค่ S3, DynamoDB

                Event-driven

                • S3 → Lambda → SQS → EC2 ASG
                • scale EC2 ตาม ความยาว queue
