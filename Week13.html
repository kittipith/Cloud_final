01 · คลิป 1

ปัญหาของการทำงานแบบเดิม (ก่อนมี DevOps)

สรุปใน 1 ประโยค

Dev ดูแลแอป Ops ดูแล infra แยกกัน พอ environment ต่างกัน แอปที่รันบนเครื่อง Dev ได้ก็ไปพังบน infra ของ Ops ทำให้ deploy ช้าและโทษกันไปมา

ทีมดูแลอะไร
Dev Team (นักพัฒนา)ดูแลแค่ ตัวแอปพลิเคชัน
Ops Team (Operations)เตรียม โครงสร้างพื้นฐาน (Infrastructure) ให้แอปรันได้ เช่น ตั้ง DNS / Domain name record, SMTP, Storage, Database, Load balancer และเซิร์ฟเวอร์

ปัญหาหลัก

  • Dev เขียนและทดสอบบนเครื่องตัวเองได้ปกติ แต่พอเอาไปรันบน infrastructure ที่ Ops เตรียมไว้กลับใช้ไม่ได้ เพราะ สภาพแวดล้อมต่างกัน — ปัญหาแบบ "works on my machine"
  • การ deploy ช้า และสองทีม โทษกันไปมา
  • สมัยก่อนแอปยังไม่ซับซ้อน การแยกกันทำงานจึงพอไปได้ แต่พอระบบใหญ่และซับซ้อนขึ้น วิธีนี้ก็ไม่ไหวแล้ว
แบบจำลอง

Deploy แอปจากเครื่อง Dev ไปยัง infra ของ Ops

เปิดแนวปฏิบัติแบบ DevOps
    จุดหลอกในข้อสอบ
    • งาน DNS, SMTP, storage, database, load balancer, server = Ops ในแบบเดิม
    • ต้นเหตุคือ environment ต่างกัน ไม่ใช่ "ไม่มี production" หรือ "Dev ทำ infra เอง"
    02 · คลิป 1 · ประเด็นสำคัญสำหรับสอบ

    DevOps คืออะไร

    สรุปใน 1 ประโยค

    DevOps ไม่ใช่เครื่องมือ แต่เป็นวัฒนธรรมและกระบวนการที่ให้ Dev กับ Ops ทำงานร่วมกันในลูปเดียว โดยใช้ automation และ Infrastructure as Code ให้ deploy ได้เร็ว เชื่อถือได้ ขยายได้ และปลอดภัย

    • DevOps ไม่ใช่เครื่องมือ แต่เป็น วัฒนธรรมการทำงาน (Culture) และกระบวนการ ที่ให้ Dev กับ Ops ทำงานร่วมกันอยู่ในลูปเดียวกัน
    • ควรมี Environment หลายระดับ (Dev / Test / Production) ที่เหมือนกัน เช่น ถ้า Production เป็น Unix บนคลาวด์ Test ก็ควรเป็นแบบเดียวกัน
    • ความสำเร็จขึ้นอยู่กับ "คนและความเข้าใจ" มากกว่าเครื่องมือ ต่อให้มี tool ดีแค่ไหน ถ้าคนไม่เข้าใจก็ไม่สำเร็จ
    • เป็น ความรับผิดชอบร่วมกัน ของทั้งสองฝั่ง ปัจจุบันยังรวม Security เข้าไปด้วย (DevSecOps)
    • ปัจจุบันเกิดตำแหน่ง DevOps Engineer ขึ้นมาก ฝั่ง Software ก็ต้องเข้าใจ Infra มากขึ้น

    เป้าหมายและข้อดีของ DevOps

    เป้าหมายความหมาย
    ทำงานร่วมกันมีประสิทธิภาพDev + Ops อยู่ในลูปเดียว
    Speed / Rapid deliveryส่งมอบซอฟต์แวร์ได้เร็ว
    Reliabilityทำซ้ำได้ถูกต้องและเชื่อถือได้
    Scaleขยายระบบได้
    Securityปลอดภัย

    หัวใจ คือทำ Automation ในทุกช่วงของการทำงาน และใช้ Infrastructure as Code เพื่อให้ deploy ซ้ำกี่ครั้งก็ได้ผลเหมือนเดิม

    ลองตอบ

    จริงหรือไม่จริง?

    จุดหลอกในข้อสอบ
    • ช้อย "DevOps คือเครื่องมือ / ชุดบริการของ AWS" — ผิด DevOps คือวัฒนธรรมและกระบวนการ
    • Test ควร เหมือน Production ไม่ใช่ต่างกันเพื่อความปลอดภัย
    • รวม security เข้ามา = DevSecOps
    03 · คลิป 1

    เฟสหลักของ DevOps

    สรุปใน 1 ประโยค

    CI (รวมโค้ด + build/test อัตโนมัติ) → CD (deploy ต่อเนื่อง) → Continuous Monitoring (เฝ้าดู) → Continuous Improvement (นำผลมาปรับ) แล้ววนกลับเป็นลูป

    เฟสทำอะไร
    Continuous Integration (CI)รวมโค้ดเข้าด้วยกันอย่างต่อเนื่อง แล้ว Build/Test อัตโนมัติ
    Continuous Delivery/Deployment (CD)ส่งโค้ดไป Deploy อย่างต่อเนื่อง
    Continuous MonitoringDeploy แล้วต้องคอย มอนิเตอร์
    Continuous Improvementดูผลจากการมอนิเตอร์แล้ว นำมาปรับปรุง ต่อ
    ดูภาพ + เรียงลำดับ

    DevOps loop

    คลิกแต่ละเฟสเพื่อดูรายละเอียดและเครื่องมือ

    เกม: คลิกเฟสตามลำดับที่ถูกต้อง

    ลำดับที่เลือก
    จุดหลอกในข้อสอบ
    • "เฝ้าดู" = Monitoring / "นำผลมาปรับ" = Improvement — อย่าสลับ
    • build/test อัตโนมัติอยู่ใน CI ส่วน deploy ต่อเนื่องคือ CD
    04 · คลิป 1

    เครื่องมือ DevOps ของ AWS

    สรุปใน 1 ประโยค

    CodeCommit เก็บโค้ด, CodeBuild build/test, CodeDeploy deploy, CodePipeline เชื่อมทุกขั้น, CloudFormation ทำ IaC, CloudWatch/X-Ray มอนิเตอร์ และ AWS Config ตรวจการตั้งค่า — แต่ไม่จำเป็นต้องใช้ของ AWS เสมอไป

    อาจารย์บอกว่า ไม่จำเป็นต้องใช้ของ AWS เสมอไป จะใช้ open source หรือเครื่องมืออื่นก็ได้ ขอให้เป็น pipeline ที่ครบ

    หมวดบริการ
    Infrastructure as CodeAWS CloudFormation (ใช้ในโปรเจกต์), AWS Systems Manager
    CI/CDCodeCommit (เก็บโค้ด), CodeBuild (Build/Test), CodeDeploy (Deploy), CodePipeline (เชื่อมทุกขั้นเป็น pipeline)
    เชื่อม repository ภายนอกAWS CodeConnections (ชื่อเดิม CodeStar Connections)
    Microservices / Container / ServerlessAmazon ECS, EKS, AWS Lambda (มีชื่อบริการหนึ่งถอดเสียงไม่ชัด อาจเป็น AWS Proton หรือ Copilot)
    Platform สำหรับเว็บแอปAWS Elastic Beanstalk
    MonitoringAmazon CloudWatch, AWS X-Ray (ดู performance และ error ของแอป)
    ตรวจสอบ ConfigurationAWS Config (ตรวจว่าทรัพยากรถูกตั้งค่าตามข้อกำหนด)

    เสริม CodeBuild อ่านขั้นตอน build จาก buildspec.yml ส่วน CodeDeploy อ่านขั้นตอน deploy จาก appspec.yml และ deploy ได้ทั้ง EC2/On-premises, Lambda และ ECS

    Documentation และสถานะบริการ

    • AWS มี Documentation และ API Reference ของแต่ละบริการให้ศึกษาต่อ
    • บางบริการ AWS เคยประกาศยกเลิกแล้วนำกลับมาใหม่ (อาจารย์พูดถึง CodeCommit) จึงควร เช็คสถานะบริการก่อนเลือกใช้ ถ้าจะเก็บโค้ดแบบ private ก็ใช้ Git repository เจ้าอื่นได้
    จับคู่

    ต้องการ… ใช้บริการอะไร

    จุดหลอกในข้อสอบ
    • CodeStar Connections → CodeConnections (ไม่ใช่ CodeCatalyst / CodeArtifact / CodeGuru)
    • CloudWatch = metric/log, X-Ray = performance/error ของแอป, AWS Config = ตรวจการตั้งค่าตามข้อกำหนด
    • CodeBuild ≠ CodeDeploy ≠ CodePipeline (build / deploy / เชื่อมทุกขั้น)
    05 · คลิป 2 · ออกสอบบ่อย

    ขั้นตอนของ CI/CD Pipeline

    สรุปใน 1 ประโยค

    Source → Build & Test → Deploy Test → Deploy Production โดย Continuous Delivery มีคนกด manual approval ก่อนขึ้น production ส่วน Continuous Deployment อัตโนมัติทั้งหมด

    1. Source: นักพัฒนาเขียนโค้ดแล้ว Push เข้า Repository
    2. Build & Test: build อัตโนมัติ ถ้าเป็นแอปแบบ container ก็สร้าง Container Image แล้วเก็บไว้ใน Registry (เช่น Amazon ECR)
    3. Deploy ไป Test Environment เพื่อทดสอบก่อน
    4. Deploy ไป Production

    ความต่างที่ออกสอบบ่อย

    Continuous DeliveryContinuous Deployment
    ก่อนขึ้น Productionต้องมีคน Review และกด Manual Approvalอัตโนมัติทั้งหมด ไม่ต้องมีคนอนุมัติ

    จำง่าย ๆ: Delivery = มี คนอนุมัติ / Deployment = เครื่องทำเองทั้งหมด

    เครื่องมือหลัก: CodeConnections, CodeCommit, CodeBuild, CodeDeploy และ CodePipeline

    แบบจำลอง

    Pipeline simulator

    ทุก stage ถูกเชื่อมและสั่งงานโดย AWS CodePipeline
    จุดหลอกในข้อสอบ
    • มี manual approval = Delivery / ไม่มี = Deployment (ช้อยหลอกชอบสลับ)
    • ทั้งสองแบบยัง deploy ไป Test ก่อน production ได้
    • แอป container: ขั้น build ต้องสร้าง image แล้วเก็บใน registry เช่น ECR
    06 · คลิป 2

    Infrastructure as Code: CloudFormation vs Terraform

    สรุปใน 1 ประโยค

    CloudFormation เป็นของ AWS เอง ความเสี่ยงต่ำถ้าใช้ AWS 100% ส่วน Terraform ฟีเจอร์เยอะกว่าแต่เป็นบุคคลที่สามที่เคยเปลี่ยน license และถูกซื้อกิจการ — และควรแยกขั้นสร้าง infra ออกจากขั้น deploy ไฟล์

    Provision หมายถึงการ สร้าง ปรับปรุง หรือลบ ทรัพยากรตามที่เขียนไว้ใน template

    AWS CloudFormationTerraform
    ผู้พัฒนาบริการของ AWS เองเครื่องมือของ บุคคลที่สาม
    ความเสี่ยงต่ำถ้าใช้ระบบบน AWS 100%เดิมเป็น open source ใช้ฟรี แต่ภายหลัง เปลี่ยนเงื่อนไข license และบริษัทผู้พัฒนา ถูกซื้อกิจการ → เสี่ยงเรื่องการเปลี่ยนแปลงหรือยกเลิก
    ฟีเจอร์โดยปกติสร้าง S3 bucket ได้แค่ bucket เปล่าฟีเจอร์เยอะ สะดวกกว่าในบางเรื่อง เช่น สร้าง S3 bucket แล้วอัปโหลดไฟล์เข้าไปได้

    เสริม HashiCorp เปลี่ยน license ของ Terraform เป็น Business Source License (BSL) ในปี 2023 และ IBM ซื้อ HashiCorp (ปิดดีลปี 2025) ชุมชนจึง fork เป็น OpenTofu

    เรื่อง Security: การให้สิทธิ์ (permission) เขียนไฟล์เข้า resource ระหว่าง deploy อาจไม่ปลอดภัย ควร แยกขั้น "สร้าง Infrastructure" ออกจากขั้น "Deploy แอป/ไฟล์" ให้ชัดเจน

    ลองเลือก + เทียบสิทธิ์

    CloudFormation หรือ Terraform และการแยกขั้น

    สิทธิ์ที่ pipeline ต้องได้: รวมขั้น vs แยกขั้น

    จุดหลอกในข้อสอบ
    • อยากลดความเสี่ยงจากเครื่องมือบุคคลที่สามบนระบบ AWS 100% → CloudFormation
    • "สร้าง bucket แล้วอัปโหลดไฟล์สะดวก" เป็นจุดเด่นของ Terraform ตามที่อาจารย์เปรียบเทียบ
    • แนวทาง security คือ แยกขั้น ไม่ใช่รวมทุกอย่างไว้ใน template เดียวหรือให้สิทธิ์ admin
    07 · คลิป 2

    CloudFormation Template, Stack และ StackSets

    สรุปใน 1 ประโยค

    เขียน template (JSON/YAML) ที่ต้องมี Resources เสมอ อัปโหลดแล้วได้ Stack ใน region เดียว ถ้าต้องการชุดเดียวกันหลาย account และหลาย region ใช้ StackSets

    • เขียน Template (JSON/YAML) แล้วอัปโหลดเข้า CloudFormation ระบบจะสร้าง Stack ขึ้นมา
    • Stack อยู่ใน Region เดียว ต้องระบุ Region ให้ชัด (ยกเว้นบริการ Global บางตัว)
    • ต้อง deploy ทรัพยากรชุดเดียวกันไป หลาย Account และหลาย Region (เช่น องค์กรที่ใช้ AWS Organizations) → ใช้ CloudFormation StackSets
    • โครงสร้าง template มีหลายส่วน แต่ ส่วนที่บังคับต้องมีคือ Resources
    AWSTemplateFormatVersion: "2010-09-09"
Description: Bucket สำหรับเว็บ
Parameters:
  Env:
    Type: String
    Default: dev
Resources:            # ส่วนเดียวที่บังคับ
  WebBucket:
    Type: AWS::S3::Bucket
Outputs:
  BucketName:
    Value: !Ref WebBucket

    เสริม ส่วนอื่นที่ไม่บังคับ: AWSTemplateFormatVersion, Description, Metadata, Parameters, Rules, Mappings, Conditions, Transform, Outputs

    08 · คลิป 2
    
  
    Serverless และ AWS SAM
    
  
    สรุปใน 1 ประโยค
    SAM เป็น open-source framework สำหรับ serverless ที่ต่อยอดจาก CloudFormation รวบ Lambda + IAM + ทรัพยากรที่เกี่ยวข้องไว้ใน template สั้น ๆ และใช้ SAM CLI ทดสอบบนเครื่องได้ก่อน deploy
    
  
      
    
    • AWS SAM (Serverless Application Model) เป็น open-source framework สำหรับสร้าง serverless application เบื้องหลังทำงานบน CloudFormation (เป็นส่วนขยายที่เขียนสั้นกว่า)
      • 
    
    • ปกติถ้าสร้าง Lambda แบบ manual ต้องตั้งค่าเองหลายอย่าง เช่น IAM Role/Policy และ S3 Bucket แต่ SAM รวบให้ใน template เดียว
      • 
    
    • SAM CLI ใช้ ทดสอบบนเครื่อง Local ได้ — execute/test ได้เลย โดยไม่ต้อง deploy ขึ้นคลาวด์จริง ช่วยเช็คว่าโค้ดทำงานถูกและเรียกบริการอื่น เช่น DynamoDB ได้
      • 
    
    • SAM ทำงานร่วมกับ CodePipeline ได้

        Flashcards
        
  
        เลือกคำตอบที่ถูกจาก 4 ตัวเลือก (กด 1–4 หรือ A–D ก็ได้) การ์ดจะพลิกเฉลยพร้อมบอกว่าตัวที่เลือกผิดเพราะอะไร ตอบผิดหรือกด "ไม่รู้" การ์ดจะวนกลับมาอีก ถ้าอยากทวนแบบเดิมให้สลับเป็นโหมด "พลิกการ์ด"
        
  
        
  
        
    
    
        
    
    
        
    
        
      
      
        
        
        
        
      
        
    
        
    
        
      
      
    
        
  
        

        



        
  
        ทบทวน
        
  
        สรุปสั้นสำหรับท่องก่อนสอบ
        
  
        
  
        
    
        DevOps
        • วัฒนธรรม ไม่ใช่แค่เครื่องมือ
        • Dev + Ops ลูปเดียว รับผิดชอบร่วม
        • สำเร็จเพราะคนและความเข้าใจ
        
    
        ปัญหาแบบเดิม
        • Dev = แอป / Ops = infra
        • environment ต่าง → works on my machine
        • deploy ช้า โทษกัน
        
    
        เป้าหมาย
        • Speed, Reliability, Scale, Security
        • หัวใจ: Automation + IaC
        • รวม security = DevSecOps
        
    
        เฟส
        • CI → CD → Monitoring → Improvement
        • แล้ววนกลับเป็นลูป
        
    
        Delivery vs Deployment
        • Delivery: manual approval ก่อน prod
        • Deployment: อัตโนมัติทั้งหมด
        
    
        Pipeline
        • Source → Build & Test → Test → Prod
        • container: image → ECR
        
    
        เครื่องมือ CI/CD
        • CodeCommit → CodeBuild → CodeDeploy
        • CodePipeline เชื่อมทั้งหมด
        • CodeStar Connections → CodeConnections
        
    
        Monitoring
        • CloudWatch metric/log
        • X-Ray performance/error
        • AWS Config ตรวจการตั้งค่า
        
    
        CloudFormation
        • Template (JSON/YAML) → Stack
        • Stack อยู่ region เดียว
        • บังคับ: Resources
        • หลาย account/region: StackSets
        
    
        CFN vs Terraform
        • CFN ของ AWS ความเสี่ยงต่ำบน AWS 100%
        • Terraform ฟีเจอร์เยอะ แต่ license เปลี่ยน / ถูกซื้อ
        • แยกขั้นสร้าง infra กับ deploy ไฟล์
        
    
        AWS SAM
        • framework serverless บน CloudFormation
        • SAM CLI ทดสอบ local ก่อน deploy
        • ใช้กับ CodePipeline ได้
        
    
        งาน
        • Activity: SAM + Lambda + API GW + DynamoDB
        • ส่ง presentation ล่วงหน้า 1 วัน
        • Lab/KC ครบเกณฑ์ → Certificate
        
  
        
  
        ตัวอย่างการตอบแบบสั้นตรงจุด
        
  
        "DevOps คือวัฒนธรรมที่ให้ Dev กับ Ops ทำงานร่วมกันในลูปเดียว ใช้ automation และ Infrastructure as Code เพื่อให้ deploy ซ้ำได้ผลเหมือนเดิม วนเป็น CI → CD → Monitoring → Improvement บน AWS ใช้ CodeCommit เก็บโค้ด CodeBuild build/test CodeDeploy deploy และ CodePipeline เชื่อมทั้งหมด ถ้ามีคนกดอนุมัติก่อนขึ้น production คือ Continuous Delivery ถ้าอัตโนมัติทั้งหมดคือ Continuous Deployment โครงสร้างพื้นฐานเขียนเป็น CloudFormation template ได้ stack ใน region เดียว (ส่วนที่บังคับคือ Resources) ถ้าหลาย account/region ใช้ StackSets และงาน serverless ใช้ SAM ที่ทดสอบบนเครื่องได้ด้วย SAM CLI"
