01 · Module 8

Compute 3 แบบ และทำไมต้องมี Container

สรุปใน 1 ประโยค

Container ใช้ kernel ของ host ร่วมกันจึงเบาและเริ่มเร็วกว่า VM แต่ยังแยกแอปออกจากกัน และรวม code + runtime + library ไว้ในตัว จึงรันที่ไหนก็ได้ผลเหมือนเดิม

Compute Service มี 3 แบบ

แบบServiceเรียนเมื่อ
Virtual MachineEC2วิชา ACA
ServerlessLambdaสัปดาห์ที่แล้ว
ContainerECS / EKS / Fargateสัปดาห์นี้

เล่าตามลำดับประวัติ

ยุค Bare Metal (เครื่องจริง) — ลง OS แล้วลง Library กับ Application ทุกตัวไว้บนเครื่องเดียวกัน

  • อัปเดต Library ให้แอป A ใช้ได้ แอป C อาจพัง เพราะ Library ชนกัน
  • เปลี่ยนเครื่องหรือเปลี่ยนฮาร์ดแวร์ ของที่เคยใช้ได้ก็อาจใช้ไม่ได้ (อาจารย์เคยต้องตามหา Wireless Adapter ชิปเซ็ตรุ่นเฉพาะ เพื่อเปิด Promiscuous Mode ดักแพ็กเก็ตด้วย Wireshark)
  • ปัญหาคลาสสิก "Works on my machine, doesn't work in production" ทุกครั้งที่ deploy ต้องมีทีม standby คอยเฝ้า

ยุค Virtual Machine — ใช้ Hypervisor เช่น VMware ESX หรือ Workstation

  • ข้อดี: แต่ละ VM เป็น Isolated Environment ถ้า C พัง A กับ B ก็ยังทำงานได้
  • ข้อเสีย: ทุก VM ต้องมี OS ของตัวเอง จึงหนักและเปลืองทรัพยากร

ยุค Container — ใช้ Container Engine เช่น Docker

  • Container ใช้ Kernel ของ Host OS ร่วมกัน และใช้ Layer ที่เป็น Read-only ร่วมกันได้ แต่ตัวแอปยังแยกกันอยู่
  • ผล: เบา (Lightweight), เริ่มทำงานเร็ว, ใช้ทรัพยากรคุ้ม (Resource Utilization)
ลองเล่น

Bare Metal vs VM vs Container — เกิดอะไรขึ้นเมื่อ...

เปรียบเทียบกับตู้คอนเทนเนอร์ขนส่ง

  • ตู้มีขนาดมาตรฐาน จะวางบนเรือลำไหนก็ส่งของได้เหมือนเดิม และช่วยจัดวางของให้คุ้มพื้นที่ (Optimization ภายใต้ Constraint คล้าย Linear Programming)
  • Software Container คือ หน่วยมาตรฐานของซอฟต์แวร์ ที่รวม Code, Runtime, System Tools และ Library ไว้ด้วยกัน รันบน Host ไหนก็ได้ผลเหมือนเดิม จึงได้ Consistency
จุดหลอกในข้อสอบ
  • "มี OS แยกทุกตัว" = VM ไม่ใช่ container
  • VM ก็ แยกกัน (isolated) — ข้อเสียของ VM คือหนัก ไม่ใช่แยกกันไม่ได้
  • Library ชนกันเป็นปัญหาของ Bare Metal
02 · Module 8

พื้นฐาน Docker

สรุปใน 1 ประโยค

Dockerfile → docker build ได้ image ที่เป็น read-only layers → docker run ได้ container ที่มี R/W layer บนสุด และเก็บ image ไว้ใน registry เช่น ECR

  • Dockerfile คือไฟล์ configuration ที่บอกว่าจะใช้ Base Image อะไร (เช่น Ubuntu 20.04), จะ Copy ไฟล์อะไรไปไว้ที่ไหน (เช่น index.html) และจะรัน Command อะไร
  • docker build สร้าง Container Image ออกมาเป็น Layer ซ้อนกัน และ ทุก Layer เป็น Read-only
  • docker run ระบบจะเพิ่ม Read-Write Layer (Container Layer) ไว้ด้านบนสุดของ Image
  • Container หลายตัวที่ใช้ Base Image เดียวกัน ใช้ Read-only Layer ร่วมกันได้ จึงประหยัดพื้นที่
  • Image เก็บใน Container Registry เช่น Amazon ECR, Docker Hub, GitLab ตอนสั่งรัน ระบบจะดึง Image มาจาก Registry
  • คำสั่งพื้นฐาน: docker build, docker images, docker run, docker stop
  • Tag คือป้ายแบบ Key/Value เช่น Name=WebServer ใช้จัดกลุ่ม ค้นหา filter และจัดการทรัพยากร
  • เหมาะกับ Microservices: ถ้า container ไหนมีปัญหา ก็ Terminate ทิ้งแล้วสร้างใหม่จาก Image เดิม ได้เร็ว โดยไม่ต้องไล่หาสาเหตุก่อน

    • Dockerfile คือสูตร, registry คือที่เก็บ image, Tag คือป้าย key/value
    03 · Module 8

    การรัน Container บน Cloud: IaaS vs Managed

    สรุปใน 1 ประโยค

    ทำเองบน EC2 ได้การควบคุมมากและถูกกว่าเมื่อ spec เท่ากัน ส่วน managed (Beanstalk/ECS/EKS) เร็วและ AWS ดูแลให้ — ควรใช้ managed เมื่อมี container มาก ต้อง scale ต้องการลดภาระ หรือต้องการ HA

    แบบ IaaS (ทำเอง)แบบ Managed / PaaS
    วิธีทำProvision EC2, VPC, Security Group, NACL, ELB เอง แล้วลง Docker หรือ K8s เองใช้ Elastic Beanstalk, ECS หรือ EKS
    ข้อดีควบคุมได้มาก และ ค่าใช้จ่ายถูกกว่าเมื่อ Spec เท่ากันเร็ว (Agility) และ AWS ช่วย Provision, Manage, Maintain ให้
    ข้อเสียต้องทำ ดูแล และตั้งค่าเองทั้งหมดควบคุมได้น้อยลง และค่าใช้จ่ายสูงขึ้น

    ถ้าเลือกแบบ Managed (ECS หรือ EKS) เลือก Infra ได้ว่าจะใช้ EC2 หรือ Fargate (Serverless)

    เมื่อไหร่ควรใช้ Managed Container Service (ออกสอบได้)

    1. ต้องดูแล Container จำนวนมาก
    2. ต้องการ Scaling ให้ทรัพยากรเพิ่ม/ลดตาม Demand
    3. ต้องการ ลดภาระงาน (Workload) ให้ Cloud Provider ดูแลแทน
    4. ต้องการ Resilience / High Availability — container มีปัญหา ระบบลบแล้วสร้างใหม่ให้อัตโนมัติ
    ช่วยตัดสินใจ

    ควรใช้ Managed หรือทำเอง?

    ความต้องการที่ชี้ไปทาง Managed
    ความต้องการที่ชี้ไปทาง IaaS

    Case study: บริษัทจุดชาร์จรถ EV

    ระบบ IoT มี container ไม่ถึง 20 ตัว รันอยู่ On-Premise ช่วงวันหยุดยาว traffic เพิ่ม 3–4 เท่า ทีมต้องมีคนเฝ้าระบบตลอดและไปเที่ยวไม่ได้ เขาถามว่าควรใช้ EKS ไหม → อาจารย์แนะนำว่า ECS ก็พอ เพราะมี HA และ scaling ได้ ถูกกว่า และง่ายกว่า ส่วน EKS เหมาะกับงานที่มี container เยอะมาก

    สิ่งที่ Managed Container Service ช่วยทำให้

    • Provisioning
    • Scheduling และ Placement — เลือกว่าจะวาง container บน EC2 ตัวไหนหรือ AZ ไหน
    • Deploy แบบ Multi-AZ
    • Launch และ Terminate
    • Scaling
    • Integration กับ AWS Service อื่น เช่น S3, DynamoDB, ELB, VPC, IAM

    ถ้าตั้ง Kubernetes Cluster เองบน EC2 ก็เชื่อม AWS Service ได้ แต่ทำยากกว่า เช่นการเชื่อมต่อแบบ private ต้องพึ่ง open-source tool ซึ่งต้องคิดเรื่องความน่าเชื่อถือใน production ด้วย

    จุดหลอกในข้อสอบ
    • "ควบคุมเองเต็มที่ / ถูกที่สุดเมื่อ spec เท่ากัน" คือข้อดีของ IaaS ไม่ใช่เหตุผลของ managed
    • container น้อย + อยากได้ HA และถูก → ECS ไม่ใช่ EKS
    • Scheduling/Placement = เลือกว่าจะวาง container ที่ EC2 ตัวไหน / AZ ไหน
    04 · Module 8

    Amazon ECS และ Amazon ECR

    สรุปใน 1 ประโยค

    ECS เป็น container orchestration ระดับ Regional ที่วาง container กระจายหลาย AZ ให้เกิด HA ส่วน ECR เป็น registry แบบ fully managed ที่ใช้กับ Docker CLI และคุมสิทธิ์ด้วย IAM

    Amazon ECS (Elastic Container Service)

    • เป็น Container Orchestration ที่ scale ได้สูง ทำ Scheduling และ Placement ให้ และเชื่อมกับ AWS Service และ Third-party ได้
    • ทำ HA ได้ โดยวาง container เดียวกันไว้ใน EC2 ที่อยู่ใน AZ A และ AZ B ถ้า AZ ใด AZ หนึ่งล่ม ระบบก็ยังทำงานได้
    • เป็น Regional Service
    • เหมาะกับระบบที่มี container ไม่มาก แต่ต้องการ HA และ resilience และอยากคุมค่าใช้จ่าย
    แบบจำลอง

    ECS service: 4 tasks กระจายหลาย AZ

      Amazon ECR (Elastic Container Registry)

      • Container Registry แบบ Fully Managed และเป็น Regional Service
      • ใช้กับ Docker CLI ได้
      • คุมสิทธิ์การเข้าถึง image ด้วย IAM
      จุดหลอกในข้อสอบ
      • ECS และ ECR เป็น Regional ไม่ใช่ global
      • ECR = registry (เก็บ image) / ECS = orchestration (รัน container)
      • ECR คุมสิทธิ์ด้วย IAM ไม่ใช่ security group และใช้กับ Docker CLI ได้

      ECS Launch Type: EC2 เทียบกับ Fargate

      สรุปใน 1 ประโยค

      EC2 launch type จ่ายตามเครื่องที่ provision คุมงบได้แต่รับไม่ไหวถ้าเกิน max ส่วน Fargate จ่ายตามที่ใช้จริง scale ตาม demand แต่ค่าใช้จ่ายคาดเดายาก

      EC2 Launch TypeFargate Launch Type
      คิดเงินจ่ายตาม EC2 ที่ Provision ไว้ (เช่น 4 เครื่อง เครื่องละ 2 vCPU / 8 GB) ไม่ว่าจะใช้เต็มหรือไม่จ่ายตาม Compute Capacity (vCPU/Memory) ที่ใช้จริง
      การ Scaleตั้ง Min/Max เองได้ เช่น สูงสุดไม่เกิน 6 เครื่องAWS Scale ให้ตาม Demand อัตโนมัติ
      ข้อดีคุมงบได้แน่นอน และควบคุมได้มากไม่ต้องดูแล Infra และรองรับ traffic ที่พุ่งขึ้นได้
      ข้อเสียถ้าคนใช้ เกินขีดจำกัด Max ระบบจะรับไม่ไหวค่าใช้จ่ายคาดเดายาก คนใช้เยอะก็จ่ายเยอะ
      เหมาะกับDemand รู้ล่วงหน้าและค่อนข้างคงที่, Workload ใหญ่, ต้องการ Optimize for Price (เช่นใช้ Reserved Instance ลดได้ 50–60%)Demand ขึ้นลง คาดเดาไม่ได้, Startup หรือ ทีมเล็ก, ระบบขนาดเล็ก, อยากลด overhead การดูแล

      แนวคิดในการเลือก: งบประมาณตายตัว เช่นหน่วยงานรัฐ → EC2 เพราะคุม cost ได้ / Performance และ User Experience สำคัญมากและ traffic คาดเดาไม่ได้ → Fargate ทั้งนี้ขึ้นกับ use case

      เสริม กับ Fargate เราไม่ต้องจัดการ EC2 ของ cluster เลย แต่จำนวน task ยังกำหนดผ่าน Service Auto Scaling ได้

        06 · Module 8

        Amazon EKS (Elastic Kubernetes Service)

        สรุปใน 1 ประโยค

        EKS คือ managed Kubernetes ที่เลือก EC2 หรือ Fargate ได้ เหมาะกับ container จำนวนมากหรือมี K8s on-prem อยู่แล้ว แต่แพงกว่า ECS

        • เป็น Managed Kubernetes และเลือก Infra ได้ทั้ง EC2 หรือ Fargate เหมือน ECS
        • เหมาะกับงานที่มี Container จำนวนมาก หรือ มี Kubernetes Cluster อยู่แล้วบน On-Premise และอยาก migrate ขึ้น AWS
        • AWS ช่วยดูแลการ Update เวอร์ชัน Kubernetes และ Patch ด้านความปลอดภัย ตามรอบเวลาอัตโนมัติ
        • ข้อเสีย: แพงกว่า ECS (เสริม EKS คิดค่า control plane รายชั่วโมงต่อ cluster เพิ่มจากค่า compute)
        ECSEKS
        เหมาะกับContainer ไม่มาก ต้องการ HA + คุมงบContainer จำนวนมาก / มี K8s เดิมอยู่แล้ว
        ความง่ายง่ายกว่าซับซ้อนกว่า (Kubernetes)
        ค่าใช้จ่ายถูกกว่าแพงกว่า
        ช่วยเลือก

        ECS หรือ EKS ดี

        เกณฑ์ "100 container" ในแบบจำลองนี้เป็นตัวเลขสมมติประกอบการอธิบาย เนื้อหาบอกแค่ "ไม่มาก" กับ "เยอะมาก"

        จุดหลอกในข้อสอบ
        • มี K8s on-prem อยู่แล้ว → EKS (ECS ไม่ใช่ Kubernetes)
        • EKS ไม่ได้ใช้ได้แค่ Fargate — เลือกได้ทั้ง EC2 และ Fargate
        • EKS แพงกว่า ECS และ AWS ช่วยอัปเดตเวอร์ชัน/patch ให้
        07 · Module 8

        AWS Elastic Beanstalk และ IAM

        สรุปใน 1 ประโยค

        Beanstalk คือ PaaS ที่อัปโหลด code แล้วสร้าง EC2 + ASG + Load Balancer ให้ โดยใช้ Instance Profile ให้ EC2, Service Role ให้ Beanstalk และ User Policy ให้คนในทีม

        • เป็น PaaS สำหรับ Deploy Web Application (คล้ายกับที่ RDS เป็น PaaS สำหรับ Database) เลือก Platform หรือภาษา อัปโหลด Code แล้วระบบจะ Launch ให้เลย
        • Beanstalk Provision EC2, Auto Scaling Group และ Load Balancer (ALB หรือ NLB) ให้เอง
        • ถ้าเลือก Multi-container Docker Platform เบื้องหลังจะเป็น ECS แต่ Beanstalk จัดการให้ ไม่ต้องสร้าง Task Definition หรือ ECS Cluster เอง (เสริม platform ชื่อนี้เป็นรุ่นเก่า ปัจจุบันคือ "ECS running on Amazon Linux 2")

          Deployment Policy ของ Elastic Beanstalk

          สรุปใน 1 ประโยค

          All at once เร็วแต่ downtime, Rolling ช้าและ capacity ลด, Rolling with additional batch ไม่ลด capacity แต่จ่ายเพิ่ม, Immutable ปลอดภัย rollback ง่ายแต่มี 2 ASG, Traffic splitting ทดสอบกับผู้ใช้จริงทีละ %

          Policyการทำงานข้อดีข้อเสีย
          All at onceอัปเดตทุก Instance พร้อมกันเร็วที่สุดมี Downtime
          Rollingอัปเดตทีละชุด (Batch) เช่น มี 10 เครื่องทำทีละ 2ลด Downtime ได้ใช้เวลานาน และ Capacity ลดลง
          Rolling with additional batchเพิ่มเครื่องชุดใหม่ก่อน (10 เป็น 12) แล้วค่อย RollingCapacity ไม่ลดลงใช้ทรัพยากรและค่าใช้จ่ายเพิ่ม
          Immutableสร้าง ASG ชุดที่ 2 ด้วยเวอร์ชันใหม่ ผ่าน Health Check แล้วค่อยย้าย Trafficปลอดภัย, Rollback ง่าย เพราะของเดิมยังอยู่ช่วงหนึ่งมี 2 ASG ค่าใช้จ่ายสูงขึ้น
          Traffic splittingคล้าย Immutable แต่ ค่อย ๆ ย้าย Traffic ทีละ % เช่นทีละ 5% (Canary Testing)ทดสอบกับผู้ใช้จริง ก่อนย้าย 100%ใช้เวลานานกว่า
          แบบจำลอง

          Deploy v2 ไปยัง 10 instances

          v1กำลังอัปเดต (ไม่รับ traffic)กำลัง launchv2

          ใน Lab ยังใช้ Aurora Serverless (RDS) เป็น database และ Lab ใช้ Classic Load Balancer ซึ่งอาจารย์บอกว่าเป็นของรุ่นเก่า งานจริงไม่จำเป็นต้องใช้แล้ว

          จุดหลอกในข้อสอบ
          • Rolling ไม่เพิ่มเครื่อง → capacity ลด / Rolling with additional batch เพิ่มเครื่องก่อน → capacity ไม่ลด
          • Immutable = สร้าง ASG ใหม่ทั้งชุด rollback ง่าย / Traffic splitting = แบ่ง % ผู้ใช้ (canary)
          • มี downtime มีแบบเดียวคือ All at once

          หลักการ Caching

          สรุปใน 1 ประโยค

          Cache เก็บข้อมูลที่ถูกอ่านบ่อยแต่เปลี่ยนไม่บ่อยไว้ใกล้ผู้ใช้ในหน่วยความจำความเร็วสูง พร้อม TTL เพื่อลด latency และลดภาระ origin/database

          Module นี้เนื้อหาไม่เยอะ ส่วนใหญ่เป็นเรื่อง Caching ที่เรียนไปแล้วใน ACA สิ่งที่เพิ่มมาสำหรับสาย Developer คือ Lambda@Edge และ CloudFront Functions

          ทำไมต้องทำ Caching

          • ลด Latency (Delay) และ Response Time ในการเข้าถึงข้อมูล
          • ลดภาระของ Origin หรือ Database
          • เก็บข้อมูลไว้ ใกล้ผู้ใช้ เช่นที่ Edge Location (กรุงเทพฯ ก็มี) ผู้ใช้จึงไม่ต้องวิ่งไปถึง origin ที่อยู่ไกล
          • Cache คือหน่วยความจำความเร็วสูงที่เก็บ ข้อมูลที่ถูกเรียกใช้บ่อย และมี TTL (Time to Live) พอหมดเวลาข้อมูลจะถูกลบออกเพื่อให้มีพื้นที่เก็บข้อมูลใหม่

          ข้อมูลแบบไหนควร Cache

          • ควร: ข้อมูลที่ ถูกอ่านบ่อยแต่เปลี่ยนไม่บ่อย เช่นงาน Read-heavy (Social Network, Game Online), งาน Compute-intensive, หรือข้อมูลขนาดใหญ่
          • ไม่ควร: ข้อมูลที่ เปลี่ยนบ่อยมาก

          Cache ได้หลายระดับ

          ระดับใช้อะไร
          Applicationใน app เอง
          DatabaseElastiCache
          WebCloudFront (CDN)
          ลองจัด

          ข้อมูลนี้ควร cache ไหม และ cache ที่ระดับไหน

          จุดหลอกในข้อสอบ
          • ข้อมูลที่ เปลี่ยนบ่อยมาก (ราคาหุ้นทุกวินาที, ยอดเงินระหว่างโอน) ไม่เหมาะกับ cache
          • Database cache = ElastiCache / Web cache = CloudFront (ช้อยหลอกมักสลับ)
          • TTL = อายุของข้อมูลใน cache ไม่ใช่เวลาดึงข้อมูลจาก origin

          Amazon ElastiCache

          สรุปใน 1 ประโยค

          ElastiCache เป็น in-memory data store แบบ fully managed มี Memcached (ง่าย) กับ Redis (ฟีเจอร์เยอะ) ใช้ได้ทั้ง Lazy Loading (เขียน cache ตอน miss) และ Write-Through (เขียน cache ทุกครั้งที่อัปเดต DB)

          • เป็น In-Memory Data Store แบบ Fully Managed ที่ scale ตาม demand ได้ (ใช้ใน Lab 9.1)
          MemcachedRedis
          ลักษณะใช้งานง่าย architecture เรียบง่าย ทำงานแบบ Network-attached RAMมีฟีเจอร์มากกว่า ตั้งค่าได้ทั้ง Cluster Mode Disabled และ Enabled
          เสริมmultithreaded, ไม่มี persistence/replicationมี replication, persistence, data structure หลากหลาย, pub/sub

          เสริม ปัจจุบัน ElastiCache รองรับ engine Valkey (fork ของ Redis OSS) เพิ่มด้วย

          ลำดับการทำงาน

          1. App ส่ง request ไปที่ ElastiCache ก่อน
          2. ถ้าเจอข้อมูล (Cache Hit) ก็ตอบกลับได้ทันที
          3. ถ้าไม่เจอ (Cache Miss) App จะไปดึงข้อมูลจาก Database แล้ว เขียนลง Cache เก็บไว้ใช้ครั้งต่อไป

          Caching Strategy 2 แบบ

          Lazy LoadingWrite-Through
          การทำงานรอให้เกิด request และ cache miss ก่อน แล้วค่อยเขียนข้อมูลลง cacheทุกครั้งที่ update database ก็เขียนลง cache ไปพร้อมกัน
          ข้อดี เสริมcache เก็บเฉพาะข้อมูลที่มีคนขอจริง, node cache ล่มก็ไม่พัง (แค่ miss)ข้อมูลใน cache เป็นปัจจุบันเสมอ
          ข้อเสีย เสริมข้อมูลอาจ เก่า (stale), request แรกช้า (miss penalty)เขียนช้าลง (write penalty), อาจเก็บข้อมูลที่ไม่มีใครอ่าน

          เสริม ใช้ TTL ร่วมกับทั้งสองแบบเพื่อจำกัดอายุข้อมูลเก่าและไม่ให้ cache เต็ม

            • อยากให้ cache เป็นปัจจุบันเสมอเมื่อ DB เปลี่ยน → Write-Through (ไม่ใช่เพิ่ม TTL)
            • "เขียนช้าลง / เก็บข้อมูลที่ไม่มีใครอ่าน" เป็นข้อเสียของ Write-Through / "ข้อมูลเก่า / request แรกช้า" เป็นของ Lazy Loading
            • "ง่าย, network-attached RAM" = Memcached / "ฟีเจอร์เยอะ, cluster mode" = Redis
            • cache miss ไม่ใช่ error — app ไปอ่าน DB แล้วเขียนลง cache

            Amazon CloudFront และ Cache Key

            สรุปใน 1 ประโยค

            CloudFront เป็น CDN ที่ cache ไว้ที่ edge โดย default cache key = domain + URL path และเพิ่ม cache hit ratio ได้ด้วยการไม่ใส่ query/header/cookie ที่ไม่จำเป็นลง key และตั้ง TTL ให้เหมาะ

            • เป็น CDN ที่ใช้เครือข่าย edge ของ AWS ทั่วโลก (ใช้ใน Lab 9.2)
            • ทำงานร่วมกับ AWS Shield, WAF และ ACM ได้
            • Origin เป็นได้หลายแบบ: S3 Bucket, EC2, Load Balancer หรือ Custom Origin อย่างเครื่อง On-Premise
            • Use case: Web Content, Video On-Demand, Live Streaming, งาน Event
            • ตัวอย่าง: เก็บไฟล์วิดีโอขนาดใหญ่ไว้ใน S3 แล้วตั้ง S3 เป็น origin ผู้ใช้ดึงไฟล์จาก edge ที่ใกล้ที่สุด จึงได้ความเร็วที่ดี

            Cache Key และ Cache Hit Ratio

            • Default Cache Key = CloudFront Distribution Domain Name + URL Path เช่น xxx.cloudfront.net/content/story-example.html
            • request ครั้งแรกเป็น Cache Miss CloudFront ไปดึงไฟล์จาก origin มาเก็บไว้ / request ครั้งที่สองด้วย key เดิมเป็น Cache Hit ได้ไฟล์จาก edge ทันที
            • Cache Hit Ratio ยิ่งสูงยิ่งดี เพราะแปลว่าผู้ใช้ไม่ต้องวิ่งไปถึง origin

            วิธีเพิ่ม Cache Hit Ratio

            1. อย่าให้ Cache Key ละเอียดเกินไป — อย่าใส่ query string, header หรือ cookie ที่ไม่จำเป็นลงใน key เช่น ไฟล์เหมือนกันแต่ cookie ID ต่างกัน แล้วใส่ cookie ลงใน key ไฟล์เดียวกันจะถูก cache แยกกันหลายชุดและแทบไม่ hit
            2. ตั้งค่า TTL ให้เหมาะสม ทั้ง Minimum, Maximum และ Default TTL

            ศึกษาเพิ่ม: เอกสาร AWS หัวข้อ "Increasing the proportion of requests that are served directly from the CloudFront caches"

            ใส่อะไรลงใน cache key เพิ่มจาก default (domain + URL path)
            จุดหลอกในข้อสอบ
            • default cache key ไม่รวม cookie, query string, header หรือ IP
            • hit ratio ต่ำเพราะ key ละเอียดเกิน → เอาส่วนที่ไม่จำเป็นออกจาก key (การลด TTL ยิ่งทำให้ miss มากขึ้น)
