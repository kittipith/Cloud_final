01

Serverless คืออะไร

สรุปใน 1 ประโยค

ยิ่งขยับจาก On-premises ไปทาง Serverless เรายิ่งดูแลเครื่องน้อยลง จนเหลือแค่ดูแลโค้ด แลกกับข้อเสียคือ cold start

ระดับการจัดการ 4 ขั้น

ยิ่งขั้นสูง เรายิ่งดูแลเครื่องน้อยลงและได้โฟกัสกับ business logic มากขึ้น

ระดับสิ่งที่ได้สิ่งที่เรายังต้องดูแล
On-premisesควบคุมได้ทุกอย่างลงทุนก้อนใหญ่, ต้องเดาความจุเอง, ติดตั้งนานเป็นเดือน, ดูแลทุกชั้นตั้งแต่ฮาร์ดแวร์
VM (EC2)ไม่ต้องซื้อฮาร์ดแวร์, ปรับขนาดได้ยังต้องดูแล OS เอง เช่น patch และ monitor
Containersรันได้ทุกที่, ใช้ทรัพยากรคุ้มขึ้น, deploy เร็วยังต้องดูแลตัว container และ cluster (ยกเว้นใช้ Fargate)
Serverlessไม่มี OS ให้ดูแล, scale อัตโนมัติ, จ่ายตามที่ใช้, มี fault tolerance ในตัว, แทบไม่ต้องบำรุงรักษาดูแลแค่ โค้ดและการตั้งค่า
อาจารย์เน้น
  • Lambda = serverless compute (รันโค้ด)
  • Fargate = serverless infrastructure สำหรับ container (รัน container โดยไม่ต้องดูแลเครื่อง)

เปรียบเทียบให้เห็นภาพ: On-premises = สร้างบ้านเอง, EC2 = เช่าบ้านทั้งหลังแต่ซ่อมเอง, Container = เช่าห้องในหอที่จัดของเองได้, Serverless = เรียก Grab มารับ จ่ายเฉพาะตอนนั่ง ไม่ต้องดูแลรถ

ลองเล่น

ใครดูแลอะไรในแต่ละระดับ

ข้อดี

    สิ่งที่ยังต้องทำ / ข้อเสีย

      แนวคิดของแอป serverless สมัยใหม่

      • แบ่งเป็นชิ้นเล็ก ๆ ที่ผูกกันหลวม ๆ (loosely coupled) ชิ้นหนึ่งพังไม่ลากชิ้นอื่นพังตาม
      • ทำงานแบบ event-driven คือทำงานเฉพาะตอนมี event มากระตุ้น เช่น มีไฟล์อัปโหลด, มีคน call API, มีข้อความเข้าคิว
      • ถ้าไม่มี event ก็ scale to zero ไม่มีค่าใช้จ่ายตอนว่าง
      • ข้อเสียที่ตามมาคือ cold start: ตอนเรียกครั้งแรก (หรือหลังว่างไปนาน) AWS ต้องเตรียม environment ใหม่ ทำให้ request แรกช้ากว่าปกติ
      จุดหลอกในข้อสอบ
      • อย่าสลับ: Lambda = compute, Fargate = container
      • "ต้อง patch / monitor OS เอง" เป็นภาระของระดับ VM (EC2) ไม่ใช่ข้อดีของ serverless
      • scale to zero → ไม่จ่ายตอนว่าง แต่ข้อเสียที่ตามมาคือ cold start
      02

      AWS Lambda

      สรุปใน 1 ประโยค

      Lambda คือบริการ serverless compute ที่รันโค้ดของเราเมื่อมี event โดยเราดูแลโค้ด ส่วน AWS ดูแลเครื่อง

      Lambda เป็นบริการ serverless compute ที่ให้เรารันโค้ดได้โดยไม่ต้องสร้างหรือดูแลเซิร์ฟเวอร์

      แบ่งหน้าที่: ลูกค้าดูแล โค้ด ส่วน AWS ดูแล เครื่อง (OS, patch, scaling, availability)

      จุดเด่น 3 ข้อ

      1. รันโค้ดเพื่อตอบสนองต่อ event
      2. scale ให้อัตโนมัติ
      3. ส่ง log และ metric ไป CloudWatch ให้เอง

      ฟีเจอร์ 6 ข้อ

      1. ใช้โค้ดของเราเองได้ (bring your own code)
      2. ทำงานร่วมกับบริการ AWS อื่นได้ (integrated)
      3. ปรับ resource และ concurrency ได้
      4. ตั้ง permission ได้ยืดหยุ่น
      5. มี availability และ fault tolerance ในตัว
      6. ไม่ต้องจ่ายตอนไม่ได้ใช้งาน (pay for value)

      เสริม คิดเงินจาก (1) จำนวน request และ (2) duration × memory ที่ตั้ง คิดละเอียดถึงระดับมิลลิวินาที

        Invocation models

        สรุปใน 1 ประโยค

        Push แบบ sync ผู้เรียกรอผลและไม่มี retry, push แบบ async เข้าคิวและ retry ได้ 0–2 ครั้ง, ส่วน pull คือ Lambda ไป poll ข้อมูลมาเป็น batch

        Push model — บริการอื่นเป็นคนเรียก Lambda

        SynchronousAsynchronous
        ตัวอย่างAPI GatewayS3 (รวมถึง SNS, EventBridge เสริม)
        การทำงานผู้เรียก รอ ผลตอบกลับLambda เอา event เข้าคิว ก่อน แล้วตอบผู้เรียกทันทีว่ารับแล้ว จากนั้นค่อยส่งให้ function
        Retryไม่มี retry ในตัว error ส่งกลับไปที่ผู้เรียก ผู้เรียกต้อง retry เองretry ได้ 0–2 ครั้ง (ค่าเริ่มต้น 2) รวมแล้วลองได้สูงสุด 3 ครั้ง
        InvocationTypeRequestResponseEvent

        Pull (polling) model — Lambda เป็นฝ่ายไปดึงข้อมูลเอง

        • Lambda ไป poll แหล่งข้อมูล แล้วเรียก function พร้อมข้อมูลเป็น batch
        • ใช้กับ Kinesis, SQS, DynamoDB Streams
        • ตั้งค่าผ่านสิ่งที่เรียกว่า event source mapping
        • เสริม เพราะ Lambda เป็นฝ่ายไปอ่าน สิทธิ์อ่านคิว/stream จึงอยู่ใน execution role ของ Lambda ไม่ใช่ resource-based policy

        Destinations (อาจารย์โชว์ในแลบ)

        • ใช้ส่งผลลัพธ์ของการเรียกแบบ async หรือ event source mapping ไปต่อที่อื่น เช่น SNS, SQS, Lambda อื่น, EventBridge
        • ตั้งได้ 2 เงื่อนไข: On failure หรือ On success
        • ใช้กับการเรียกแบบ sync (เช่น API Gateway) ไม่ได้ เพราะผลถูกส่งกลับให้ผู้เรียกโดยตรงอยู่แล้ว
        แบบจำลอง

          • "retry 2 ครั้ง" ≠ "ลอง 2 ครั้ง" — ครั้งแรก 1 + retry 2 = 3 ครั้ง
          • ไม่มี InvocationType ชื่อ Async หรือ Sync
          • Sync ไม่ใช่ "retry ไม่ได้เลย" แต่ Lambda ไม่ retry ให้ ฝั่งผู้เรียก (client) ต้องจัดการเอง

          Lambda permissions — สิทธิ์มี 2 ฝั่ง

          สรุปใน 1 ประโยค

          ใครจะเรียก Lambda ได้ ตั้งที่ resource-based policy ส่วน Lambda จะไปใช้บริการอื่นได้ ตั้งที่ IAM execution role

          ทิศทางคำถามตั้งผ่าน
          ขาเข้าใครมีสิทธิ์ เรียก Lambda?Resource-based policy (function policy) เช่นอนุญาต s3.amazonaws.com ให้ lambda:InvokeFunction
          ขาออกLambda มีสิทธิ์ เข้าถึง บริการอื่นไหม?IAM execution role เช่น s3:GetObject, s3:PutObject, dynamodb:Query

          จุดหลอกในข้อสอบ

          • ไม่มี log เลย = function ยังไม่เคยถูกเรียก ปัญหาอยู่ก่อนถึงโค้ด
          • เสริม pull model (SQS/Kinesis): Lambda เป็นฝ่ายไปอ่าน สิทธิ์จึงอยู่ใน execution role

            • ทำ function ให้ stateless อย่าเก็บ state ไว้ในเครื่อง เพราะการเรียกครั้งถัดไปอาจไปรันคนละ environment
              • 
    
            • ใส่ เฉพาะสิ่งที่จำเป็น (package เล็ก → cold start เร็ว)
              • 
    
            • reuse runtime environment ชั่วคราว ที่มีอยู่ เช่น สร้าง DB client / SDK client นอก handler เพื่อให้การเรียกครั้งถัดไปที่ได้ environment เดิม (warm) ใช้ connection เดิมได้
              •

            Good vs Bad

              จุดหลอกในข้อสอบ
    
                
      
              • "reuse environment" คือใช้ซ้ำเพื่อ ประสิทธิภาพ (cache, connection) ไม่ได้แปลว่าให้ฝาก state ที่ต้องถูกต้อง ไว้ในนั้น
                • 
      
              • λ เรียก λ ได้ทางเทคนิค — แต่ไม่ควรทำ (ช้อย "IAM ไม่อนุญาต" เป็นช้อยหลอก)
                • 
      
              • เขียนผลลัพธ์ลง bucket เดียวกับที่ trigger = recursive

              08
              
  
              Deployment
              
  
              สรุปใน 1 ประโยค
              deploy ได้ทั้ง .zip และ container image (ผ่าน ECR), publish แล้วได้ version ที่แก้ไม่ได้, alias เป็นตัวชี้ไป version และ layer คือ library ที่ใช้ร่วมกัน
              
  
              
    
              หัวข้อรายละเอียด
              
    
      
              .zip archiveเลือก runtime ตอนสร้าง function แล้ว zip โค้ดกับ dependencies อัปโหลดขึ้นไป
              
      
              Container imageเลือก runtime และ Linux distribution ตอนสร้าง image แล้วอัปโหลดขึ้น Amazon ECR
              
      
              Versioningตอน publish จะได้ version ที่ แก้ไขไม่ได้ (immutable) เช่น :1 ส่วน $LATEST คือตัวที่กำลังแก้อยู่ (แก้ได้)
              
      
              Aliasเช่น PROD เป็น ตัวชี้ ไปยัง version ที่ต้องการ ข้อดีคือ event source ไม่ต้องเปลี่ยน ARN ทุกครั้งที่ออก version ใหม่ แค่ย้าย alias
              
      
              Layerslibrary ที่ หลาย function ใช้ร่วมกัน ได้
              
      
              Runtimeมี runtime สำเร็จรูปให้ และสร้าง custom runtime เองก็ได้
              
                  
  
              

  
              
    
              ลองเล่น

                เสริม alias ยังแบ่ง traffic ระหว่าง 2 version ได้ (เช่น 90/10) สำหรับทำ canary release
                
  
                จุดหลอกในข้อสอบ
    
                  
      
                • version ที่ publish แล้ว immutable — $LATEST ต่างหากที่แก้ได้ (ช้อยมักสลับกัน)
                  • 
      
                • alias ย้ายได้ นั่นคือหน้าที่ของมัน
                  • 
      
                • ให้ trigger ชี้ $LATEST ใน production ไม่ดี เพราะโค้ดเปลี่ยนตลอดขณะพัฒนา
                  • 
      
                • container image → ECR ไม่ใช่ S3 หรือ Layers

                Monitoring และ AWS X-Ray
                
  
                สรุปใน 1 ประโยค
                CloudWatch เก็บ log/metric ของแต่ละ function (ดู Init Duration = cold start) ส่วน X-Ray trace request ข้ามหลายบริการเป็น service map
                
  
                ทำไมแอปสมัยใหม่ monitor ยาก
                
  
                • resource มี อายุสั้น (environment เกิดแล้วหายไป)
                • มี อุปกรณ์และบริการเยอะ
                • ออก release ถี่
                
  
                CloudWatch Logs
                
  
                Log group /aws/lambda/<ชื่อ function>→Log stream→Log events

                บรรทัด REPORT ใน CloudWatch
                
    
                
      
                
        
        
      
                
      
                
      
                
    
                
  
                

  
                AWS X-Ray
                
  
                  
    
                • trace request ที่วิ่งผ่านหลายบริการ แล้ววาดเป็น service map
                  • 
    
                • ใช้หา latency, หาจุดผิดปกติ (outlier), debug ระบบแบบ distributed
                  • 
    
                • เปิดใช้กับ Lambda ได้ใน คลิกเดียว (active tracing)
                  • 
    
                • ถ้าใช้ X-Ray SDK จะเก็บข้อมูลการเรียก API ผ่าน AWS SDK ได้ด้วย (เช่นเห็นว่าการเรียก DynamoDB ใช้เวลาเท่าไร)
                  • 
  
                
  
                
    
                ดูภาพ
                X-Ray service map
                
    
                
      
      
                
      
                
    
                
  
                
  
                แยกให้ออก
                CloudWatch = log + metric ของแต่ละ function / X-Ray = เส้นทาง request ข้ามหลายบริการ
                
  
                จุดหลอกในข้อสอบ
    
                  
      
                • Init Duration = cold start (ไม่ใช่ Duration หรือ Billed Duration) และมีเฉพาะการเรียกที่เป็น cold start
                  • 
      
                • รูปแบบ log group คือ /aws/lambda/<name> ช้อยหลอกมักสลับลำดับคำ
                  • 
      
                • อยากเห็นเวลาเรียก DynamoDB ภายใน function → ต้องใช้ X-Ray SDK เพิ่ม

                เปลี่ยน mock endpoint ใน API Gateway จากแลบก่อน ให้เป็น endpoint จริงที่ใช้ Lambda ดึงข้อมูลจาก DynamoDB
                
  
                
    
                เช็กลิสต์
                ขั้นตอนแลบ (ตามที่โชว์ในแลบ)
                
    
                
      
                  
    
                  
  
                  
  
                  ขั้นตอนนี้เรียงจากคำอธิบายแลบแบบย่อ อาจไม่ตรงกับที่อาจารย์ทำทุกคลิก
                  
  
                  จุดหลอกในข้อสอบ
    
                  • แลบนี้ต้องมีสิทธิ์ทั้ง 2 ฝั่ง: API Gateway เรียก Lambda (resource-based policy) + Lambda อ่าน DynamoDB (execution role)
                  • provisioned concurrency ไม่ใช่เงื่อนไขจำเป็นของการเชื่อม API Gateway กับ Lambda
                  
  
                  
  
                  
  
                  

                  



                  
  
                  ทบทวน
                  
  
                  Flashcards
                  
  
                  คลิกการ์ดหรือกด Space เพื่อพลิก แล้วบอกตัวเองว่าจำได้หรือยัง การ์ดที่ยังจำไม่ได้จะวนกลับมาอีก
                  
  
                  
    
    
                  
      
      
                  
        
        
        
      
                  
    
                  
    
                  
      
      
    
                  
  
                  

                  



                  
  
                  ทบทวน
                  
  
                  สรุปหน้าเดียวก่อนเข้าห้องสอบ
                  
  
                  
  
                  
    
                  บทบาท
                  • Lambda = serverless compute
                  • Fargate = serverless container
                  
    
                  Sync
                  • API Gateway
                  • รอผล, Lambda ไม่ retry
                  • RequestResponse
                  
    
                  Async
                  • S3
                  • เข้าคิว, retry 0–2 (รวม 3 ครั้ง)
                  • Event
                  
    
                  Poll
                  • Kinesis / SQS / DynamoDB Streams
                  • event source mapping, batch
                  
    
                  Destinations
                  • async + event source mapping
                  • On success / On failure
                  
    
                  Permissions
                  • ใครเรียก Lambda → resource-based policy
                  • Lambda ไปเรียกใคร → execution role
                  
    
                  Handler
                  • handler(event, context)
                  • event = ข้อมูล trigger
                  • context = ข้อมูล runtime
                  
    
                  ตัวเลข
                  • Memory 128–10,240 MB (CPU ตาม)
                  • Timeout 1 วิ – 15 นาที
                  • Concurrency 1,000/Region (soft)
                  
    
                  Concurrency
                  • Reserved = กันโควตา + เพดาน + ฟรี
                  • Provisioned = อุ่นเครื่อง แก้ cold start + เสียเงิน
                  
    
                  Deployment
                  • Version immutable, $LATEST แก้ได้
                  • Alias = pointer, Layer = library ร่วม
                  • image → ECR
                  
    
                  Monitoring
                  • Init Duration = cold start
                  • Log group /aws/lambda/<name>
                  • X-Ray = service map ข้ามบริการ
                  
    
                  Best practice
                  • ห้าม recursive, ห้าม λ เรียก λ ตรง ๆ
                  • stateless, init client นอก handler
                  
  
                  
  
                  ตัวอย่างการตอบแบบสั้นตรงจุด
                  
  
                  "Lambda คือที่รันโค้ดตาม event โดยไม่ต้องดูแลเซิร์ฟเวอร์ จ่ายเฉพาะตอนรัน ถ้าเรียกแบบ sync ผู้เรียกจะรอผลและไม่มี retry ส่วนแบบ async จะเข้าคิวและ retry ได้ 2 ครั้ง สิทธิ์มี 2 ฝั่ง คือ event source ต้องมีสิทธิ์เรียก Lambda และ Lambda ต้องมี execution role เพื่อเข้าถึงบริการอื่น ถ้าเจอ cold start ให้แก้ด้วย provisioned concurrency"
